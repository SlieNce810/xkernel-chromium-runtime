## 0. 一页速览

### 0.1 基础任务要做什么（赛题原文）

> 基于给出的 x-kernel QEMU 基线，配置图形、输入、文件系统和网络所需内核能力，启动 Weston 或其他图形界面系统，并建立稳定可重复的图形会话。
> 在 AArch64 QEMU（统一评测平台）使用可用的虚拟显示设备和图形后端运行图形界面；通过 X11、Xwayland、原生 Wayland 或其他方案启动 Chromium，创建窗口并显示指定本地 HTML 页面。
> **基础验收**：图形界面能够成功启动并稳定运行；显示服务或 compositor 持续工作。参赛队伍需提交**图形界面截图、启动日志、运行命令和稳定性证明**。

### 0.2 得分拆解与判据

| 评分项 | 分 | 判据 | 证据要求 |
|---|---|---|---|
| 图形会话启动 | 10 | 成功启动图形会话 | screendump 截图 + 启动日志 |
| 图形稳定运行 | 10 | 连续 ≥10 分钟且 compositor 无退出 | 稳定性证明（进程存活证据） |
| Chromium 启动创建窗口 | 10 | Chromium 成功启动并创建窗口 | screendump 截图 + 日志 + **完整运行命令** |
| 渲染指定 HTML | 10 | 正确渲染组委会指定 HTML 页面 | screendump 截图（页面内容可辨认） |

**核心纪律**：功能类指标「达标即满分、**缺证据按项计 0 分**」。做出来了但没留证据 = 0 分。
**唯一认可的截图方式**：QEMU monitor `screendump`。主机录屏仅作演示辅助，**不作为验收依据**【原文】。

### 0.3 完成标准（Definition of Done）

全部满足才算基础任务收工：

- [ ] AArch64 QEMU（纯 TCG）启动，Weston 图形会话建立
- [ ] `screendump` 截出可辨认的 Weston 桌面画面（≥1 张）
- [ ] compositor 连续存活 ≥10 分钟，有可核查的存活证据
- [ ] Chromium 创建窗口，`screendump` 截出浏览器窗口
- [ ] Chromium 正确渲染本地 HTML 页面（画面内容与源文件一致）
- [ ] 上述每一项都配齐：**截图 + 日志 + 完整命令**，归档到 `evidence/`
- [ ] 该版本已 `git tag` 冻结（这是后续 before/after 的基线）

### 0.4 十二步流程总览

| 步 | 名称 | 环境 | 关键动作 | 产出 |
|---|---|---|---|---|
| S0 | 准备 Linux 主机 | Linux | 定机器、装依赖 | 可用主机 |
| S1 | 环境自检 | Linux | `scripts/env-check.sh` | `env.txt` 指纹 |
| S2 | 取仓库与基线配置 | Linux | clone + `cp qemu_defconfig .config` | `.config` |
| S3 | 无图形冒烟构建 | Linux | `make build` + `make run` | 能进 shell |

| S5 | 注入 uapps | Linux | `make uapps` | `xk-weston-start` 就位 |
| S6 | 带图形首次启动 | Linux | `GRAPHIC=y ACCEL=n` | 看到画面 |
| S7 | screendump 取证 | Linux | monitor `screendump` | PPM/PNG 截图 |
| S8 | guest 内补齐包仓库 | guest | 开 community 源 + `apk add weston` | Weston 装好 |
| S9 | Weston 稳定 10 分钟 | Linux+guest | 长稳 + 存活证据 | 稳定性证明 |

## 1. 硬事实速查（本次实测，可直接引用进报告）

### 1.1 内核基线配置

基线文件 `platforms/kplat-aarch64/qemu_defconfig`（**赛题第七节所指的 qemu_defconfig 基线**，文件真实存在，与上游 `main` 分支逐字节一致）【实测】：

```ini
# Weston graphics requires the virtio GPU and input drivers.
KFEAT_DRIVER_VIRTIO_GPU=y
KFEAT_DRIVER_VIRTIO_INPUT=y
```

关键推论【实测自 `drivers/Kconfig` + `Kconfig`】：

| 符号 | 默认值 | 含义 |
|---|---|---|
| `KFEAT_DRIVER_VIRTIO_GPU` | **无默认** | 必须显式 `=y`，否则无虚拟显示设备 |
| `KFEAT_DRIVER_VIRTIO_INPUT` | **无默认** | 必须显式 `=y`，否则无输入设备 |
| `KFEAT_DRIVER_VIRTIO_BLK` | `y` | 磁盘会自动挂载，无需手动开 |
| `KFEAT_DRIVER_VIRTIO_NET` | `y` | 网络默认开 |
| `KFEAT_DRIVER_VIRTIO_SOCKET` | `y` | vsock 默认开 |
| `KFEAT_DRIVER_VIRTIO_RNG` | `y` | 随机数源默认开 |
| `KFEAT_VIRTIO_BUS_PCI` | choice 默认 | 走 PCI 总线，设备名后缀 `pci` |
| `KFEAT_DISPLAY` / `KFEAT_INPUT` | `y` | 显示/输入子系统默认开 |
| `NR_CPUS` | `4`（范围 1–8） | `--smp` 缺省即 4 |

**结论**：**厂商已经把图形所需的内核侧配置好了，你不需要改内核就能启动 Weston。** 基础任务的第一阶段不要浪费时间去啃内核配置。

### 1.2 `make run` 实际生成的 QEMU 命令行【实测自 `xtask/xkmake/src/qemu.rs`】

不带 `GRAPHIC=y` 时：追加 `-nographic`。
带 `GRAPHIC=y` 时，追加：

```
-device virtio-gpu-pci -vga none -serial mon:stdio
```

`-serial mon:stdio` 的含义（**这是取证机制的关键**）：**串口和 QEMU monitor 复用同一个 stdio**。
→ 在 QEMU 窗口/终端里按 `Ctrl-A` 再按 `c`，即从「串口」切到「monitor」，反之亦然。

其余固定参数：

```
-m <memory>  -smp <cpus>
-cpu cortex-a76 -machine virt,gic-version=3 -kernel <xkernel_*.bin>
-device virtio-blk-pci,drive=disk0
-drive id=disk0,if=none,format=raw,file=<DISK_IMG>
-device virtio-net-pci,netdev=net0
-netdev user,id=net0,hostfwd=tcp::61005-:5555,hostfwd=udp::61005-:5555
-device virtio-rng-pci,rng=host_rng0
```

### ⚠️ 1.2.1 严重缺口：`make run` 默认**不挂 virtio-input**

赛题第七节（一）3 要求设备组合为 `virtio-gpu-pci`、**`virtio-input`**、`virtio-blk`、`virtio-net`。
但把 `xtask/xkmake/src/qemu.rs` 的 `add_devices()` 逐段看完，它**只**添加 blk / net / gpu / vsock / rng 五类设备，
**全文检索 `input|keyboard|mouse|tablet` 零命中**【实测】。

旁证：官方 `xk-weston-start` 给 weston 传了 `--continue-without-input`——这个参数的作用正是
"没有输入设备也继续启动"，反过来说明**默认环境确实没有输入设备**。

**后果**：

| 影响面 | 说明 |
|---|---|
| guest 内 `/dev/input/event*` | 不存在 |
| 基础任务 | 不受影响（图形 + 渲染仍能拿 40 分） |
| **决赛「键盘输入回显与鼠标点击跳转」4 分** | **拿不到** |
| Weston 输入 | 官方脚本靠伪造 `/run/udev/data/c13:{1,2}` + `--continue-without-input` 兜着，但**没有真实设备可读** |

**修复**（必须显式加 QEMU 设备参数；注意这是"命令行缺项"，不是内核配置问题——
内核侧 `KFEAT_DRIVER_VIRTIO_INPUT=y` 基线已经开了）：

```bash
# 手工方式：把 QEMU_ARGS 作为单个 make 变量传入（值含空格，必须整体引用）
make run GRAPHIC=y ACCEL=n MEM=4g SMP=4 \
  QEMU_ARGS='-device virtio-keyboard-pci -device virtio-mouse-pci'

# 用配套脚本：--with-input 会自动拼好并保证不被拆成两个 argv
python3 scripts/run-session.py --cwd ~/x-kernel \
  --make-args 'GRAPHIC=y ACCEL=n MEM=4g SMP=4' --with-input \
  --duration 300 --out evidence/s6-with-input
```

**验证方式**（这是判断有没有生效的唯一硬标准）：

```sh
# guest 内
ls -l /dev/input/
# 期望：event0 / event1（两个 virtio-input 设备）
cat /proc/bus/input/devices 2>/dev/null | head -40   # 若该文件可用
```

**设备枚举顺序需要实测确认，不要假设**。官方脚本伪造的是 `c13:1`=鼠标、`c13:2`=键盘
（`c13` 是 `/dev/input` 的主设备号，`:N` 是次设备号，即 eventN）【实测原文】。
所以脚本预期「event1 是鼠标、event2 是键盘」。你用 `virtio-keyboard-pci` + `virtio-mouse-pci`
得到的是 event0/event1，**顺序可能与之不符** → 需要按实测结果调整伪造文件的次设备号，
否则 libinput 会把键盘当鼠标（或反之），表现为"键按了没反应/鼠标乱跳"。

三种候选设备与取舍：

| QEMU 设备 | 事件类型 | 说明 |
|---|---|---|
| `virtio-mouse-pci` | 相对坐标（REL） | 与官方脚本的 `ID_INPUT_MOUSE` 语义一致，**首选** |
| `virtio-tablet-pci` | 绝对坐标（ABS） | 对合成器更友好（无需指针加速），但 udev 标签应给 `ID_INPUT_TABLET`，与官方脚本不符 |
| `virtio-keyboard-pci` | 按键（KEY） | 键回显必需 |


加速后端选择逻辑【实测】：

```rust
fn hardware_accel(guest: KernelArch) -> Option<&'static str> {
    let arch_matches = matches!((env::consts::ARCH, guest),
        ("x86_64", X86_64) | ("aarch64", Aarch64) | ("riscv64", Riscv64));
    if !arch_matches { return None; }          // ← 宿主架构与 guest 不同 → 自动 TCG
    match env::consts::OS {
        "macos" => Some("hvf"),
        "linux" if !is_wsl() && is_dev("/dev/kvm") => Some("kvm"),
        _ => None,
    }
}
```

**两个极其有用的推论**：

1. **在 x86_64 Linux 主机上跑 AArch64 guest，`-accel` 根本不会被添加 → 天然就是纯 TCG**。这自动满足赛题「初赛禁用 KVM/HVF」的要求。
2. **WSL 会被显式排除**（`is_wsl()` 检查 `/proc/sys/kernel/osrelease` 是否含 `microsoft`），所以 WSL2 里也不会误用 KVM。

但为了证据链自证清白，**仍然显式传 `ACCEL=n`**（它会加 `--no-accel`，从而绝不加 `-accel`）。

### 1.4 rootfs 与 uapps

`make rootfs` 从 `https://gitee.com/openkylin/x-kernel-image/releases/download/rootfs` 下载
`x-kernel-<ROOTFS_VARIANT>-aarch64.img.xz`，解压后 `cp` 成 `disk.img`。
变体：`debian-openrc`（默认）/ `alpine-busybox` / `debian-busybox`。

**实测压缩体积**：

| 变体 | 压缩体积 | 备注 |
|---|---|---|
| `alpine-busybox` | **9.5 MiB** | 最小；`xk-weston-start` 用 `apk`，与之匹配 |
| `debian-busybox` | 32.1 MiB | |
| `debian-openrc` | 32.7 MiB | 默认，带 openrc（agetty 自动登录、更完整的 profile） |

> **推断（需实测确认）**：`xk-weston-start` 只用 `apk` 装包，说明官方预期搭配 **Alpine 系 rootfs**。但 `alpine-busybox` 极小，`/etc/profile.d` 是否存在、是否有可用的登录 shell 需首启确认。若 Alpine 路线受阻，`debian-openrc` 是自然的备选（但要自己写 apt 逻辑，不能直接用官方脚本的 `apk` 分支）。

`make uapps` 把 `uapps/*/uapp.toml` 声明的文件用 `debugfs -w` 注入 `disk.img`，并生成 `/etc/profile.d/99-autostart.sh`。
官方 `uapps/weston-start/uapp.toml`【实测】：

```toml
[package]
name = "weston-start"
enabled = true
order = 90

[[install]]
src = "xk-weston-start"
dest = "/usr/local/bin/xk-weston-start"   # mode 0755

[[install]]
src = "weston-terminal"
dest = "/usr/bin/weston-terminal"          # mode 0755

[[autostart]]
name = "weston-start"
command = "/usr/local/bin/xk-weston-start"
background = false
check_alive = true
exit = false
```

即：**开机加载 profile 时自动执行 `xk-weston-start`**。

### 1.5 `xk-weston-start` 到底做了什么（逐段解读）【实测原文】

| 段 | 行为 | 对基础任务的意义 |
|---|---|---|
| `install_deps` | `apk add weston weston-backend-drm weston-shell-desktop weston-clients weston-xwayland xwayland xterm xclock seatd`；失败降级为 `apk add weston seatd` | **需要网络 + community 仓库**，否则直接 `exit 1` |
| 准备运行时 | `mkdir -p /run/user/0`（700）、`/tmp/.X11-unix`（1777） | Wayland socket / X11 socket 的前置目录 |
| **伪造 udev 数据** | 写 `/run/udev/data/c13:1`（鼠标）、`c13:2`（键盘），含 `ID_INPUT` / `ID_SEAT=seat0` | **绕过"无 udev/uevent/sysfs"**，让 libinput 认设备 |
| 起 seatd | `seatd -g root -l debug >/tmp/seatd.log 2>&1 &` | seat 管理兜底 |
| 起 weston | `env XDG_RUNTIME_DIR=/run/user/0 WESTON_DISABLE_ATOMIC=1 weston --backend=drm-backend.so --renderer=pixman --drm-device=card0 --seat=seat0 --continue-without-input --idle-time=0 --xwayland --log=/tmp/weston.log &` | 主链路；**`pixman` = 纯软件渲染**（因上游 DRM 无 render node / 无 GEM execbuf） |
| 等 wayland socket | 轮询 `/run/user/0/wayland-*`，最多 5 秒 | 失败即 `exit 1` |
| 起 X11 客户端 | 等 `/tmp/.X11-unix/X0` → 起 `xterm`，等日志出现 `created wm` → 起 `xclock` | Xwayland 链路自检 |
| **稳定性记录** | 后台循环每 **30 秒**写一次 `date` + `ps`（weston/Xwayland/xterm/xclock）到 **`/tmp/weston-watch.log`** | **这就是现成的"稳定性证明"原始素材！** |

三个可用的环境变量【实测】：

| 变量 | 取值 | 作用 |
|---|---|---|
| `XK_WESTON_CLIENT` | `xterm` / `xclock` / `xterm,xclock`（默认）/ `none` / `weston-simple-shm` | 启动哪些客户端；**`none` 表示只起 Weston 不起客户端** |
| `XK_WESTON_WAIT` | `1` | 前台挂住不退出（便于观察） |

> **建议**：第一次验证图形链路时用 `XK_WESTON_CLIENT=none`，把变量收敛到「DRM + Weston」这一段，避免 Xwayland 的噪声混淆判断。

### 1.6 guest 内装 Weston / Chromium 的包仓库真相【实测自 Alpine CDN 目录索引】

| 包 | 仓库 | 版本（v3.21） | 体积 |
|---|---|---|---|
| `weston` | **community** | 14.0.0-r1 | 591 K |
| `weston-backend-drm` | **community** | 14.0.0-r1 | 64 K |
| `weston-clients` / `weston-shell-desktop` / `weston-xwayland` | **community** | 14.0.0-r1 | 各 25–730 K |
| `weston-terminal` | community | 14.0.0-r1 | 51 K |
| `chromium` | **community** | 136.0.7103.113-r0 | **101 MiB** |
| `chromium-swiftshader` | community | 同版本 | 8 MiB |

- 两者**都不在 `main`**。若 guest 的 `/etc/apk/repositories` 只有 `main`，`apk add` 会失败。
- Chromium 各分支版本：v3.19=124、v3.20=131、v3.21=136、v3.22=142、edge=152。
- **Chromium 装完约需数百 MB 空间**，而 `alpine-busybox` 镜像压缩后才 9.5 MiB → **必须扩容**（S4）。
- `chromium-swiftshader` 提供软件 OpenGL。上游 DRM 无 render node / 无 GEM execbuf【实测 `io/drmdevice/docs/design.md`】，所以 Chromium 大概率需要 `--disable-gpu` 或软件 GL 路径。

## 2. 运行环境职责划分：本机（Windows）vs Linux 主机

### 2.1 判断依据（不是偏好，是硬约束）

| 约束 | 说明 |
|---|---|
| `xkmake` 是 Rust 工程，但 `make` 目标依赖 Unix 工具 | Makefile 里使用 `sed` / `curl` / `xz` / `debugfs` / `mkfs.ext4` / `test -f` / `$$()`，均为 Unix shell 语义 |
| `make uapps` 依赖 `debugfs -w -f <cmdfile> disk.img` | e2fsprogs 的 debugfs，**Windows 无原生可用实现** |
| uapps prepare 阶段需要 `aarch64-linux-musl-gcc` | musl.cc 交叉工具链，面向 Linux 主机分发 |
| **赛题硬要求 QEMU ≥ 8.0 + AArch64 guest + 纯 TCG** | 本机（Windows 侧与 WSL 侧）实测**均未安装 QEMU**（`qemu-system-aarch64` 不在 PATH，常见安装路径也不存在）【本次实测，见 2.4】 |
| 评分数据必须出自纯 TCG | 需要能稳定控制与复现的 Linux 环境 |

**结论**：**Linux 主机是构建与取证的唯一权威环境。** 本机的价值在于「编辑 / 观察 / 处理 / 归档」，而不是「跑」。

### 2.2 分工表（照这个执行）

| 工作项 | Windows 本机 | Linux 主机 | 说明 |
|---|---|---|---|
| 读源码、写 patch、Git 管理 | ✅ | ✅ | 本机可做，但 `make` 必须回 Linux |
| `make defconfig / rootfs / uapps / build / run` | ❌ | ✅ **必须** | 依赖 debugfs / musl-cross / Unix 工具 |
| QEMU 图形启动 | ❌ | ✅ **必须** | 本机无 QEMU |
| `screendump` 取证 | ❌ | ✅ **必须** | 唯一验收证据来源 |
| 纯 TCG 性能数据 | ❌ | ✅ **必须** | 赛题硬要求 |
| PPM → PNG 转换（截图归档） | ✅ | ✅ | 纯 Python 脚本，两边都能跑 |
| HTML 测试页编写与本地浏览器预览 | ✅ | ✅ | 本机浏览器先验证页面"应该是什么样" |
| 截图正确性比对（像素 / 结构） | ✅ | ✅ | 本机处理更舒服 |
| 演示录屏 / 视频剪辑（10 分演示项） | ✅ | ⚠️ | 本机有更好的工具链 |
| 文档撰写与报告 | ✅ | ✅ | |
| **可选**：QEMU for Windows 跑预构建镜像做**功能冒烟** | ⚠️ 可选 | — | 见 2.3 |

### 2.3 关于"本机仅用于功能性测试"的准确表述

你想在本机做功能性测试是可行的，但要划清界线：

**本机（Windows）可以做的功能性测试**：
把 Linux 主机上构建出的两个产物拷过来，**只验证"能不能跑起来"**：

```powershell
# 从 Linux 主机拷（示例）
scp user@linux:~/x-kernel/disk.img .
scp user@linux:~/x-kernel/target/xkmake/kplat-aarch64/release/xkernel_aarch64-qemu.bin .
```

然后在 Windows 装 QEMU for Windows（≥ 8.0），手工拼同样的命令行：

```powershell
qemu-system-aarch64.exe -m 2g -smp 4 `
  -cpu cortex-a76 -machine virt,gic-version=3 `
  -kernel .\xkernel_aarch64-qemu.bin `
  -device virtio-blk-pci,drive=disk0 `
  -drive id=disk0,if=none,format=raw,file=.\disk.img `
  -device virtio-gpu-pci -vga none `
  -device virtio-input-host-pci,id=kbd `
  -display gtk -serial mon:stdio
```

**本机测试的边界（必须严格遵守）**：

| 可以做 | 不可以做 |
|---|---|
| 验证内核能否启动、串口有无输出 | ❌ **不得**用本机结果作为评分证据 |
| 验证 Weston / Chromium 进程能否起来 | ❌ **不得**用本机的 `screendump` 当验收截图 |
| 快速试错参数组合（省 Linux 主机的等待时间） | ❌ **不得**在本机采集任何性能数据 |
| 提前发现"明显不可能"的方案 | ⚠️ 本机通过 ≠ Linux 通过（QEMU 版本/后端差异） |

**推荐做法**：本机不要装 QEMU，改成 **SSH 驱动 Linux 主机**（见 2.4）。这样只有一套环境、一套真相，避免"本机能跑、评测跑不了"的经典事故。若确实要本机冒烟，请在证据目录里显式标注 `platform: windows-smoke, NOT-EVIDENCE`。

### 2.4 本机实况（2026-09-20 用 `scripts/env-check.sh` 实测）

本机有两个"Linux 侧"，都查了：

| 环境 | 实况 | 能否作为构建/取证主机 |
|---|---|---|
| **Windows 侧** | `qemu-system-aarch64` 不存在；无 `debugfs`/`resize2fs`/`make` 原生实现 | ❌ 不能 |
| **WSL2 Ubuntu 22.04.5** | `git` / `make` / `curl` / `xz` / `python3` / `cc` / **`debugfs`** / **`resize2fs`** / `e2fsck` / `truncate` / `dumpe2fs` **全部 OK**；**缺 QEMU**、**缺 rustc** | ⚠️ 见下 |

WSL2 侧的宿主机指纹（`env-check.sh` 原始输出）：

```
OS          : Ubuntu 22.04.5 LTS
Kernel      : 5.15.167.4-microsoft-standard-WSL2
架构        : x86_64          CPU 型号 : AMD Ryzen 7 8845HS w/ Radeon 780M
CPU 逻辑核  : 16              内存     : 15Gi total / 7.8Gi available
```

**判断（务必按这个来）**：

| 用途 | WSL2 Ubuntu 22.04 | 原生 Linux（T490 / 桌面机） |
|---|---|---|
| 快速试错、验证"这条路能不能走通" | ✅ 可以 | ✅ |
| 构建 x-kernel / 注入 uapps | ✅ 工具齐备（只差 Rust） | ✅ |
| **产出评分证据（screendump / 10 分钟稳定）** | ⚠️ 不建议 | ✅ **必须用这个** |
| **性能数据采集** | ❌ 不要 | ✅ |
| 答辩现场复现 | ❌ | ✅ |

**不建议用 WSL 出证据的三条理由**（可直接写进报告）：

1. **OS 指纹不标准**：赛题第七节（二）4 要求注明"操作系统"供交叉核验，`5.15.x-microsoft-standard-WSL2` 不是评测平台的操作系统，评委可能不认。
2. **额外噪声层**：WSL2 的 IO / 调度 / 内存回收都经过一层虚拟化，TCG 本就慢，再叠加一层会放大波动，与"波动范围"要求相反。
3. **Ubuntu 22.04 自带 QEMU 是 6.2**，低于赛题要求的 8.0，需要额外源或源码编译——装完还得与真实评测环境对齐。

**如果要在这台机器上推进**，最低成本路径是：
Windows/WSL 只做「编辑 + 试错」，把构建与取证放到 T490 原生 Ubuntu（26.04，自带 QEMU 更新）；或用一台桌面机装 Ubuntu 24.04。
**在 WSL 里补 QEMU 和 Rust 也是可行的**（xkmake 会主动排除 WSL 的 KVM，天然纯 TCG），但请把它明确定位为"开发环境"，证据仍回原生 Linux 出。

### S0 · 确定并准备 Linux 主机

| 项 | 内容 |
|---|---|
| **作用** | 建立唯一权威的构建与取证环境 |
| **环境** | Linux（Ubuntu 22.04/24.04 或 26.04） |
| **前提** | 有 sudo 权限；能访问 gitee.com（下载仓库与 rootfs） |

**操作**

```bash
# 1) 基础工具
sudo apt update
sudo apt install -y git make curl xz-utils e2fsprogs build-essential pkg-config \
                    python3 socat

# 2) QEMU（版本必须 ≥ 8.0，赛题硬性要求）
sudo apt install -y qemu-system-arm qemu-system-common
qemu-system-aarch64 --version      # 必须 >= 8.0

# 3) Rust 工具链
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y

rustup target add aarch64-unknown-none-softfloat

# 4) AArch64 musl 交叉工具链（uapps prepare 阶段要用）
cd /tmp
curl -LO https://musl.cc/aarch64-linux-musl-cross.tgz
sudo tar -C /opt -xzf aarch64-linux-musl-cross.tgz
echo 'export PATH=/opt/aarch64-linux-musl-cross/bin:$PATH' >> ~/.bashrc
source ~/.bashrc
aarch64-linux-musl-gcc --version
```

**输入**：一台可联网的 Linux 主机。
**预期结果**：`qemu-system-aarch64 --version` ≥ 8.0；`aarch64-linux-musl-gcc` 可用；`cargo`/`rustc` 可用。
**验证方式**

```bash
qemu-system-aarch64 --version
rustup target list --installed | grep aarch64-unknown-none-softfloat
which debugfs resize2fs mkfs.ext4
```

四个命令全部有正常输出，才算通过。

**常见问题**

| 现象 | 原因 | 排查方向 |
|---|---|---|
| `apt` 装不到 `qemu-system-arm` | 源未更新 / Ubuntu 版本过旧 | `sudo apt update`；或改用 `snap`/源码编译；确认 ≥ 8.0 |
| QEMU 版本 < 8.0 | 发行版自带版本旧 | 从源码编译，或加 PPA；**版本不达标不要往下走** |
| musl.cc 下载极慢/失败 | 网络 | 换镜像或挂代理；工具链**只影响 uapps 里需要交叉编译的项**，纯脚本型 uapp 不需要 |
| Rust 装完 `cargo` 找不到 | 没 source env | `source "$HOME/.cargo/env"`，或重开 shell |

### S3 · 无图形冒烟：先证明内核能起来

| 项 | 内容 |
|---|---|
| **作用** | **隔离变量**。先不带图形跑通「构建 → 启动 → 进 shell」，这样后面图形起不来时可以确定问题在图形侧，而不是内核/rootfs 侧 |
| **环境** | Linux 主机 |
| **前提** | S2 完成 |

**操作**

```bash
cd ~/x-kernel

# 只编译，不跑
make build

# 打印将要执行的 QEMU 命令（不真正启动）

# 真正启动（此阶段不带 GRAPHIC，会自动加 -nographic）
make run
```

**输入**：`.config` 就绪。
**预期结果**

1. `make build` 在 `target/xkmake/kplat-aarch64/<profile>/` 下产出 bundle（含 `xkernel_aarch64-qemu.bin`、`kernel.debug.elf`）。
2. `--dry-run` 打印完整 `qemu-system-aarch64 ...` 命令，**此时应能看到 `-nographic`**。
3. `make run` 出现 PL011 串口日志，最终进入 guest shell（提示符形如 `/ #` 或 `#`）。

**验证方式**

```bash
ls -l target/xkmake/kplat-aarch64/*/
# 串口里执行：
#   uname -a
#   ls /
#   cat /proc/version 出得来
```

**常见问题**

| 现象 | 原因 | 排查方向 |
|---|---|---|
| `make build` 失败：找不到 target | 没装 `aarch64-unknown-none-softfloat` | `rustup target add aarch64-unknown-none-softfloat` |
| `make build` 失败：host target 解析异常 | Rust 版本太新/太旧导致 `rustc -vV` 解析差异 | 换 Rust stable 最新版；看报错里的具体 crate |
| 卡在 `alloc` 报错 | 未选分配器 | 基线 defconfig 里 `KFEAT_ALLOC_BUDDY`/`TLSF` 均未设 → 用默认，不要乱改 |
| 串口无输出 | `-nographic` 未生效 / 终端问题 | 确认 `--dry-run` 输出里有 `-nographic`；换纯净终端（避免 IDE 内置终端吞控制字符） |
| 起不来且打印 panic | 内核问题 | `make symbolize LOG=<bundle>/qemu.log` 把裸地址符号化 |
| 卡住不返回 | QEMU 正常在跑 | 退出用 `Ctrl-A x` |

### S4 · 准备 rootfs 并**扩容**（关键，容易漏）

| 项 | 内容 |
|---|---|
| **作用** | 拿到 guest 根文件系统，并**扩大可用空间**——否则 S8 装 Chromium（101 MiB 包）必然 `ENOSPC` |
| **环境** | Linux 主机 |
| **前提** | S3 通过 |

**操作**

```bash
cd ~/x-kernel

# 1) 下载并准备基础镜像（Alpine 系，与官方 apk 脚本匹配）
make rootfs ROOTFS_VARIANT=alpine-busybox

# 2) 看它现在多大
ls -l disk.img
du -h disk.img

# 3) 扩容到 4 GiB（raw ext4 镜像可以直接扩）
cp disk.img disk.img.orig                      # 留个干净副本备用
truncate -s 4G disk.img
e2fsck -f -y disk.img
resize2fs disk.img

# 4) 验证
ls -l disk.img
dumpe2fs -h disk.img 2>/dev/null | grep -E 'Block count|Block size|Free blocks'
```

**输入**：能访问 gitee release（下载 rootfs）。
**预期结果**

- `x-kernel-alpine-busybox-aarch64.img` 下载并解压成功（压缩包约 9.5 MiB）。
- `disk.img` 从原始尺寸扩到 **4 GiB**，`resize2fs` 报告 `The filesystem on disk.img is now ... blocks long.`
- `dumpe2fs -h` 显示 `Free blocks` 有大量空闲（应 > 800000）。

**验证方式**

```bash
# 确认文件系统没坏
e2fsck -fn disk.img && echo "fs clean"
# 确认里面确实有 profile.d（uapps 的 autostart 依赖它）
debugfs -R "ls -l /etc/profile.d" disk.img
```

**常见问题**

| 现象 | 原因 | 排查方向 |
|---|---|---|
| `make rootfs` 下载 404 | `ROOTFS_VARIANT` 拼错 | 只能用 `alpine-busybox` / `debian-busybox` / `debian-openrc` |
| `resize2fs` 报 "Nothing to do" | 没先 `truncate` 把文件变大 | 顺序必须是 `truncate` → `e2fsck -f` → `resize2fs` |
| `e2fsck` 报 "filesystem is mounted" | 镜像被别的东西占着 | 确认没有 QEMU 在跑；镜像文件不是 loop 挂载状态 |
| `debugfs -R "ls /etc/profile.d"` 报不存在 | 该 rootfs 变体没有 profile.d | **这是硬阻塞**：`make uapps` 会失败。换 `debian-openrc`，或自建 rootfs |
| 扩容后 guest 认不到新空间 | 内核/文件系统缓存 | 重启 QEMU；确认 guest 内 `df -h` |

> **设计权衡说明（可写进报告）**：把扩容放在 `make uapps` **之前**，是因为 uapps 用 `debugfs -w` 就地改镜像，镜像只增不减；先扩好空间可以避免"注入到一半失败"。另外注意 **`make uapps` 不要依赖 `make rootfs`**——官方文档明确要求二者独立，否则重跑 `make rootfs` 会把你注入的文件全部覆盖掉。

### S5 · 注入 uapps（把 `xk-weston-start` 放进镜像）

| 项 | 内容 |
|---|---|
| **作用** | 把官方的 Weston 启动器和 autostart 钩子装进 `disk.img`，让 guest 开机自动拉起图形 |
| **环境** | Linux 主机 |
| **前提** | S4 完成，`disk.img` 存在 |

**操作**

```bash
cd ~/x-kernel

# 先看看有哪些 uapp 会被装（dry-run 不写盘）
cargo run --manifest-path xtask/Cargo.toml -p uapp -- \
  install --uapps-dir uapps --disk-img disk.img --select all --dry-run 2>&1 | tail -40

# 正式注入（只装 weston-start 更干净；不指定 UAPPS 则装全部）
make uapps UAPPS=weston-start
```

**输入**：`disk.img` 已扩容；`uapps/weston-start/uapp.toml` 存在。
**预期结果**：安装摘要打印出 2 个 install 项 + 1 个 autostart 项。

**验证方式**（这是"注入是否真的成功"的硬验证）

```bash
debugfs -R "stat /usr/local/bin/xk-weston-start" disk.img
debugfs -R "stat /usr/bin/weston-terminal"       disk.img
debugfs -R "cat /etc/profile.d/99-autostart.sh"  disk.img
```

预期：前两条显示普通文件、mode 含 `0755`；第三条能打印出 autostart 脚本内容，且其中有
`/usr/local/bin/xk-weston-start`。

**常见问题**

| 现象 | 原因 | 排查方向 |
|---|---|---|
| `disk image not found` | 没跑 `make rootfs` | 回 S4 |
| 报 `/etc/profile.d` 不存在 | rootfs 变体不含该目录 | 换 rootfs 变体（见 S4 排查） |
| prepare 阶段失败 | 某个 uapp 需要交叉编译而 musl-gcc 不在 PATH | `export PATH=/opt/aarch64-linux-musl-cross/bin:$PATH`；或只装 `weston-start`（纯脚本，无需编译） |
| 重复注入后目录乱了 | `debugfs mkdir` 对已存在目录会报错（官方文档说明这是可接受的） | 不用管；必要时从 `disk.img.orig` 重建 |
| 注入后 `make rootfs` 又跑了一次 | 文件被覆盖 | **永远不要在注入后重跑 `make rootfs`**；要重置就用 `make rootfs-uapps` |

### S6 · 带图形首次启动（纯 TCG）

| 项 | 内容 |
|---|---|
| **作用** | 把内核替换成"能出画面"的形态，并第一次看到 Weston 是否起来 |
| **环境** | Linux 主机（**建议用 tmux/独立终端**，因为 monitor 共用 stdio） |
| **前提** | S5 完成；`disk.img` 已注入 uapps |

**操作**

```bash
cd ~/x-kernel

# 先确认命令会长什么样（不会真启动）
#   注意：必须是 XKMAKE_ARGS='--dry-run'；写成 make run --dry-run 会被 make
#   自己的 dry-run 截获，只会打印 cargo 命令行，看不到 QEMU 真实参数
make run GRAPHIC=y ACCEL=n MEM=4g SMP=4 XKMAKE_ARGS='--dry-run'

# 正式启动
#   1) 显式补上 virtio-input（xkmake 默认不加，见 1.2.1）
#   2) 先把 QEMU 打印出来的完整命令存进证据（这就是"完整运行命令"）
mkdir -p ~/中电杯/evidence/s6-first-graphic
make run GRAPHIC=y ACCEL=n MEM=4g SMP=4 \
     QEMU_ARGS='-device virtio-keyboard-pci -device virtio-mouse-pci' \
  2>&1 | tee ~/中电杯/evidence/s6-first-graphic/qemu-console.log
```

**输入**：`.config` 已含 `KFEAT_DRIVER_VIRTIO_GPU=y` / `KFEAT_DRIVER_VIRTIO_INPUT=y`。
**预期结果**

`--dry-run` 的输出中**必须包含**：

```
-device virtio-gpu-pci -vga none -serial mon:stdio
-device virtio-keyboard-pci -device virtio-mouse-pci   # ← 必须自己加，见 1.2.1
```

且**不应出现** `-accel kvm`、`-accel hvf`、`-accel tcg,thread=multi` 之外的加速参数（`ACCEL=n` 时干脆不出现 `-accel`）。

> 顺便用这一行自证合规（可直接写进证据目录）：
> ```bash
> grep -Eo '\-accel [a-z,=0-9]+' <证据>/cmd.txt && echo '⚠️ 有加速后端，初赛数据不可用' || echo '✅ 无加速后端，纯 TCG'
> ```

真运行时：串口打印内核启动日志，随后 `xk-weston-start` 的 `[weston-start]` 系列日志出现。

**⚠️ 第一次跑大概率会看到这一段失败，这是预期的**：

```
[weston-start] updating apk indexes
...
ERROR: unable to select packages: weston (no such package)
[weston-start] missing command after install:
  weston
  seatd
```

原因：`weston` 在 Alpine 的 **community** 仓库，而 rootfs 默认只启用了 `main`【实测】。→ 去 S8 修复。

**验证方式**

```bash
# monitor 方式（见 S7）：看设备是否被发现
(qemu) info qtree              # 应看到 virtio-gpu / virtio-input 设备
```

guest 串口内：

```sh
ls -l /dev/dri/                # 期望存在 card0
ls -l /dev/input/              # 期望存在 event0 / event1
cat /tmp/weston.log 2>/dev/null | head -30
```

**常见问题**

| 现象 | 原因 | 排查方向 |
|---|---|---|
| 报 `qemu-system-aarch64: -device virtio-gpu-pci: ...` | 本机 QEMU 太旧 | 升级 QEMU ≥ 8.0 |
| `--dry-run` 里没有 `virtio-gpu-pci` | `.config` 里 GPU 没开，或 `GRAPHIC` 没传 | `grep VIRTIO_GPU .config`；确认命令里有 `GRAPHIC=y` |
| 报 `the kernel enables virtio devices but no virtio bus is configured` | `KFEAT_VIRTIO_BUS_*` 全没选 | `make menuconfig` 选 PCI |
| 窗口一闪就退 / `Could not initialize SDL/GTK` | 无声环境却用了默认图形前端 | 加 `XKMAKE_ARGS='-- -display none'`（monitor 仍在 stdio，screendump 照常可用） |
| 终端里 control 字符乱飞 | `-serial mon:stdio` 与 IDE 终端冲突 | **改用真实终端或 tmux**，别用 IDE 内置终端 |
| `/dev/dri/card0` 不存在 | DRM 设备未注册 | 看内核日志中 drmdevice / display backend 的初始化行；确认 `io/drmdevice` 在构建里 |
| Weston 报 `no drm device` | `card0` 名字不对 | 官方脚本已写死 `--drm-device=card0`；确认 guest 内 `/dev/dri/` 下确实叫 `card0` |

### S7 · `screendump` 取证（**本手册最关键的一步**）

| 项 | 内容 |
|---|---|
| **作用** | 产出**赛题唯一认可的截图证据**。这一步做不对，20+20 分直接归零 |
| **环境** | Linux 主机 |
| **前提** | S6 已让 QEMU 带图形在跑 |

#### 7.1 原理（先讲清为什么这么做）

`GRAPHIC=y` 时 xkmake 生成的是 `-serial mon:stdio`，即**串口 + QEMU monitor 复用一个 stdio**。
所以取证流程是：**切到 monitor → 执行 `screendump` → 切回串口**。

| 动作 | 按键 |
|---|---|
| 串口 → monitor | `Ctrl-A` 然后 `c` |
| monitor → 串口 | 再次 `Ctrl-A` 然后 `c` |
| 退出 QEMU | `Ctrl-A` 然后 `x` |

在 monitor 里执行：

```
screendump /tmp/weston-20260920-1530.ppm
```

`-vga none` 已由 xkmake 加上，virtio-gpu 是唯一显示设备，所以不需要指定 `device` 参数。

#### 7.2 方式 A：手工（第一次务必手工做一遍）

```bash
# 在跑着 QEMU 的终端里：
#   1) 按 Ctrl-A 放开，再按 c        → 出现 (qemu) 提示符
#   2) 输入：
screendump /tmp/evidence/weston-base.ppm
#   3) 再按 Ctrl-A 放开，再按 c      → 回到串口
```

**验证方式**：`ls -l /tmp/evidence/weston-base.ppm` 文件存在且 > 10 KB；转成 PNG 后打开看得到 Weston 桌面。

#### 7.3 方式 B：脚本化（推荐，用于 10 分钟长稳的周期性取证）

```bash
cd ~/中电杯

# 一次性：启动 QEMU 会话，自动周期截图 + 全量日志（默认 600 秒，每 60 秒一张）
python3 scripts/run-session.py \
  --cwd ~/x-kernel \
  --make-args 'GRAPHIC=y ACCEL=n MEM=4g SMP=4' \
  --duration 600 \
  --interval 60 \
  --out evidence/s9-weston-10min
```

脚本会做四件事：① 把 `make run` 的完整命令行与全部控制台输出落盘；② 周期性地向 monitor 注入 `screendump`；③ 记录每次截图的时间戳；④ 结束时生成 `manifest.txt`（含宿主机指纹 + tag + 命令原文）。

**输入**：`make` 可用；Python 3；`disk.img` 已准备好。
**预期结果**：`evidence/s9-weston-10min/` 下出现 `console.log`、`screenshots/*.ppm`、`timestamps.csv`、`manifest.txt`。
**验证方式**

```bash
ls -l evidence/s9-weston-10min/screenshots/
python3 scripts/ppm2png.py evidence/s9-weston-10min/screenshots/*.ppm
```

PNG 打开后能看到画面，即取证成功；把 PNG 打开逐张确认内容。

#### 7.4 常见问题

| 现象 | 原因 | 排查方向 |
|---|---|---|
| `Ctrl-A c` 无反应 | 终端把 `Ctrl-A` 吞了（IDE 内置终端、某些 tmux 配置） | 换真实终端；tmux 下先用 `Ctrl-B :` 确认 prefix 不是 `C-a`；必要时把 tmux prefix 改成 `C-b` |
| monitor 里 `screendump` 报 `no surface` | 显示设备尚未初始化（启动太早） | 等到串口出现 Weston 日志后再截 |
| `screendump` 报 `Could not open file` | 目标目录不存在 | 先在**主机**上 `mkdir -p`；路径是**主机**路径，不是 guest 路径 |
| PPM 打开是黑屏 | Weston 还没画出东西 / 只在启动早期 | 延后截图时间；确认 `/tmp/weston.log` 没有报错 |
| 截出来的分辨率不对劲 | display 契约固定几何、无 mode enumeration | 属已知局限【实测 `drivers/contracts/display/docs/design.md`】，当固定值处理即可 |
| 用主机录屏替代 | **不可用作验收证据** | 必须用 screendump；录屏只放演示视频 |

### S8 · guest 内补齐 `community` 包仓库并安装 Weston（**必做的一次性修复**）

| 项 | 内容 |
|---|---|
| **作用** | 解决"官方脚本 `apk add weston` 必然失败"的问题，让图形真正装上 |
| **环境** | **guest 内**（通过串口 shell） |
| **前提** | S6 已启动到 guest shell；guest 网络可达（virtio-net + user net，DNS 走 10.0.2.3） |

**先确认问题**

```sh
# guest 内
cat /etc/alpine-release
cat /etc/apk/repositories
apk update
apk search -x weston          # 大概率找不到
apk search -x chromium        # 大概率找不到
```

**修复：启用 community 仓库**

```sh
# guest 内（POSIX sh）
VER=$(cut -d. -f1,2 /etc/alpine-release)
MIRROR=https://dl-cdn.alpinelinux.org/alpine
grep -q "$MIRROR/v$VER/main" /etc/apk/repositories 2>/dev/null || \
  echo "$MIRROR/v$VER/main" >> /etc/apk/repositories
grep -q "$MIRROR/v$VER/community" /etc/apk/repositories 2>/dev/null || \
  echo "$MIRROR/v$VER/community" >> /etc/apk/repositories
cat /etc/apk/repositories

apk update
apk search -x weston | head
```

> 也可以不改 `/etc/apk/repositories`，改用一次性参数：
> `apk add --repository=$MIRROR/v$VER/community weston`

**安装 Weston 全家桶**

```sh
apk add --no-cache weston weston-backend-drm weston-shell-desktop \
                   weston-clients weston-xwayland xwayland xterm xclock seatd
```

**输入**：guest 能访问 `dl-cdn.alpinelinux.org`；`/` 有足够空间（S4 已扩到 4G）。
**预期结果**：`apk` 成功安装；`which weston seatd weston-simple-shm` 都能找到。
**验证方式**

```sh
for c in weston seatd weston-simple-shm xterm xclock; do
  printf '%-20s %s\n' "$c" "$(command -v $c || echo MISSING)"
done
df -h /        # 确认剩余空间仍充裕
```

期望：全部非 `MISSING`。

**常见问题**

| 现象 | 原因 | 排查方向 |
|---|---|---|
| `apk update` 卡住/超时 | guest 网络不通 / DNS 不工作 | `ping 10.0.2.2`；`cat /etc/resolv.conf` 应为 `nameserver 10.0.2.3`；确认 `make run` 没传 `NET=n` |
| `unable to select packages: weston (no such package)` | community 未启用 | 回上面"修复"段 |
| `ERROR: ... No space left on device` | 镜像没扩容 | 回 S4；注意扩容必须在**关机状态**下做 |
| `apk: command not found` | rootfs 不是 Alpine 系 | 换成 `alpine-busybox`，或改走 apt（Debian 系）路线 |
| 装完仍 `MISSING` | 装到了非预期路径 | `find / -name 'weston' -type f` 定位；检查 `/usr/bin` |
| 重启后装的包没了 | 根文件系统以只读挂载 | guest 内 `mount | head` 看 `/` 是否 `rw`；只读需改内核/挂载方式 |

**装完先别急着重启，手工拉一次 Weston 验证**（把变量收敛到 DRM+Weston）：

```sh
# guest 内 —— 先清掉可能残留的进程
pkill -x weston 2>/dev/null; pkill -x seatd 2>/dev/null; sleep 1

# 只起 Weston，不起 X11 客户端
XK_WESTON_CLIENT=none /usr/local/bin/xk-weston-start

# 看结果
tail -40 /tmp/weston.log
ls -l /run/user/0/
```

预期：脚本打印 `[weston-start] weston is running`，`/run/user/0/` 下出现 `wayland-0` socket，`/tmp/weston.log` 无致命错误（`Fatal` / `failed to create`）。

> **此时回 S7 截一张图**——这将是你的第一张"图形会话启动"证据（10 分）。

**把配好的镜像冻结下来（强烈建议）**

```bash
# 主机侧，QEMU 关闭后
cd ~/x-kernel
mkdir -p images
cp disk.img images/dev-baseline-weston.img
sha256sum images/dev-baseline-weston.img | tee images/dev-baseline-weston.sha256
```

之后所有运行都改用这个镜像（**用 `DISK_IMG` 这个 make 变量，不要用 `XKMAKE_ARGS`**——
后者带空格的值在跨层传参时极易被拆成两个参数、被 make 当成构建目标）：

```bash
make run GRAPHIC=y ACCEL=n MEM=4g DISK_IMG=images/dev-baseline-weston.img
```

> **为什么必须冻结**：`xk-weston-start` 每次启动都会 `apk update` + `apk add`，这会让每次运行的网络依赖、包版本、耗时都不同 → **破坏可复现性**，也让 10 分钟稳定性测试和性能测量失去意义。冻结成固定镜像后，评测环境不联网也能跑。

### S9 · Weston 连续稳定 ≥10 分钟 + 稳定性证明

| 项 | 内容 |
|---|---|
| **作用** | 拿满「连续稳定运行不少于 10 分钟且 compositor 无退出」这 10 分 |
| **环境** | Linux 主机 + guest |
| **前提** | S8 完成，Weston 能手工拉起 |

**操作（一条命令完成启动 + 长稳 + 周期取证）**

```bash
cd ~/中电杯
python3 scripts/run-session.py \
  --cwd ~/x-kernel \
  --make-args 'GRAPHIC=y ACCEL=n MEM=4g SMP=4 DISK_IMG=images/dev-baseline-weston.img' \
  --duration 660 \
  --interval 60 \
  --with-input \
  --send '90:XK_WESTON_CLIENT=none /usr/local/bin/xk-weston-start' \
  --out evidence/s9-weston-10min
```

同时**在 guest 内采集存活证据**（这是"稳定性证明"的实质内容）：

```sh
# guest 内，另开一条（或让脚本注入）：
while true; do
  echo "=== $(date -Is) ==="
  busybox ps | grep -E 'weston|seatd|Xwayland' | grep -v grep
  cat /proc/uptime
  sleep 30
done | tee /tmp/stability-10min.log
```

官方脚本**已经在做这件事**：`xk-weston-start` 每 30 秒把 `date` + `ps` 快照写进 `/tmp/weston-watch.log`【实测原文】。**直接用这个文件即可**：

```sh
# guest 内
wc -l /tmp/weston-watch.log
tail -20 /tmp/weston-watch.log
```

**输入**：冻结镜像；Weston 已装好。
**预期结果**

- 运行满 **660 秒**（>10 分钟，留余量）。
- `/tmp/weston-watch.log` 里 **≥20 条** 30 秒间隔的 `date` 记录，且每条后面 `ps` 都能看到 `weston` 进程 → 这就是"compositor 持续工作"的直接证明。
- `screenshots/` 下 ≥10 张 PPM，画面一致（没有黑屏/花屏加剧）。
- 主机侧 `console.log` 无 `panic`、无 `Oops`。

**验证方式**

```bash
cd ~/中电杯/evidence/s9-weston-10min

# 1) 时长够了
grep -c '^====' console.log

# 2) 截图数量与时间跨度
ls screenshots/*.ppm | wc -l
cat timestamps.csv

# 3) 没有崩溃关键字
grep -Ei 'panic|oops|BUG:|segfault|killed' console.log && echo '⚠️ 有异常' || echo '干净'

# 4) 转 PNG 后目视检查首尾两张
python3 ../../scripts/ppm2png.py screenshots/*.ppm
```

**常见问题**

| 现象 | 原因 | 排查方向 |
|---|---|---|
| 5–10 分钟后 Weston 退出 | `--idle-time=0` 已禁屏保，但仍可能 OOM / panic | 看 `/tmp/weston.log` 尾部；`dmesg` 有无 OOM；关注内存（决赛资格线 1.5 GB） |
| 截图从某张开始变黑 | compositor 死了但 QEMU 还活着 | 与 `/tmp/weston-watch.log` 的时间戳对照，定位退出时刻 |
| 时间戳跨度 < 10 分钟 | TCG 太慢，脚本超时退出 | 提高 `--duration`；或先确认 QEMU 进程仍存活再停表 |
| Weston 反复重启 | autostart 钩子被多次触发 | 确认 `/etc/profile.d/99-autostart.sh` 里的 `XKERNEL_AUTOSTART_DONE` 守卫生效（官方生成脚本含此守卫） |
| 长时间跑后主机负载高 | TCG 单核打满 | 正常现象；测量时记录 `loadavg`，别在此期间跑别的重活 |

### S10 · 安装并启动 Chromium

| 项 | 内容 |
|---|---|
| **作用** | 拿「Chromium 成功启动并创建窗口」这 10 分 |
| **环境** | guest 内（安装 + 启动），Linux 主机（取证） |
| **前提** | S8（community 已开）、S9（Weston 稳定）完成 |

**1) 安装**

```sh
# guest 内
apk add --no-cache chromium chromium-swiftshader
chromium --version
```

- `chromium` 包 **101 MiB**（v3.21 = 136.0.7103.113）【实测】。
- `chromium-swiftshader` 提供软件 GL（8 MiB）。因为上游 DRM 无 render node / 无 GEM execbuf【实测】，GPU 加速路径不可用，需要软件渲染兜底。
- **耗时提示**：TCG 下解包几百 MB 会非常慢（分钟到十几分钟量级）。装完务必重新冻结镜像（见 S8 末尾），避免每次重装。

**2) 启动（按推荐顺序逐个试，每试一个都记录结果）**

需要 Weston 已经在跑，并且知道 Wayland socket 名：

```sh
# guest 内
pgrep -x weston || XK_WESTON_CLIENT=none /usr/local/bin/xk-weston-start
export XDG_RUNTIME_DIR=/run/user/0
echo $XDG_RUNTIME_DIR
ls /run/user/0/                 # 找到 wayland-0 或 wayland-1
export WAYLAND_DISPLAY=wayland-0
```

| 尝试 | 命令 | 目的 |
|---|---|---|
| ① 原生 Wayland | `chromium --ozone-platform=wayland --no-sandbox --disable-gpu --disable-dev-shm-usage about:blank` | **首选主路线** |
| ② X11（经 Xwayland） | `DISPLAY=:0 chromium --ozone-platform=x11 --no-sandbox --disable-gpu about:blank` | 兜底路线 |
| ③ 软件 GL | 在 ① 上加 `--use-gl=swiftshader` | 绕开 GPU |
| ④ GPU 进程内联 | 在 ① 上加 `--in-process-gpu` | 规避多进程 GPU 进程 IPC 问题 |
| ⑤ 单进程（**仅调试**） | 加 `--single-process` | 定位问题，**不作交付形态** |

**关键参数说明（必须理解，否则无法写报告）**

| 参数 | 为什么需要 |
|---|---|
| `--no-sandbox` | 上游**无 `unshare`/`setns`**，Chromium 沙箱不可用，必须关掉 |
| `--disable-dev-shm-usage` | 上游**无 tmpfs → 无 `/dev/shm`**，Chromium 默认共享内存路径不可用 |
| `--ozone-platform=wayland` | 选择 Ozone 平台适配层（赛题参考资料 5） |
| `--disable-gpu` | 无 render node / 无 GEM execbuf，GPU 路径不可用 |

**输入**：Weston 运行中、`XDG_RUNTIME_DIR` / `WAYLAND_DISPLAY` 正确。
**预期结果**：Chromium 进程启动，Weston 桌面上出现浏览器窗口；串口日志有 Chromium 的启动输出。
**验证方式**

```sh
# guest 内
busybox ps | grep -E 'chromium|zygote' | grep -v grep
ls /proc/$(pidof chromium)/task | wc -l      # 线程数，正常是几十
```

主机侧：回 S7 方式 A/B **截一张图**，应能看到 Chromium 窗口。这就是「Chromium 成功启动并创建窗口」的证据。

**⚠️ 必须记录"完整运行命令"**：赛题对这项明确要求"提供 screendump 截图、日志与完整运行命令"，三者缺一不可。把最终可用的那条 Chromium 命令原文（含环境变量导出）写进 `evidence/`。

**常见问题（按概率排序）**

| 现象 | 根因 | 排查方向 |
|---|---|---|
| 起不来，报无法连接 display | `XDG_RUNTIME_DIR` / `WAYLAND_DISPLAY` 不对 | `ls /run/user/0/` 确认真实 socket 名；注意 socket 名可能是 `wayland-1` |
| 报 `/dev/shm` 相关错误 | 无 tmpfs | 加 `--disable-dev-shm-usage`；这是**必加**项 |
| 报 sandbox 相关错误 | 无 `unshare`/`setns` | 加 `--no-sandbox` |
| 卡在 GPU 初始化 | 无 render node | 加 `--disable-gpu`；再不行加 `--use-gl=swiftshader` |
| 起来但窗口全黑 | 软件渲染/共享内存路径问题 | 加 `--in-process-gpu`；检查 `chromium --enable-logging=stderr --v=1` 输出 |
| renderer 进程反复崩溃 | V8 JIT 的 `mprotect` RW→RX 语义 / `memfd` sealing 不完整 | 这是**中阶任务的正式缺口**，先用 `--single-process` 确认主进程能否渲染，再把它登记进缺口清单 |
| 直接 `Killed` | 内存不足 / 被 OOM | 提内存 `MEM=4g`；查 `dmesg`；注意决赛资格线 **峰值内存 ≤1.5 GB** |
| `apk add` 报空间不足 | 忘了扩容 | 回 S4；**扩容必须在关机状态做**，装过东西的镜像扩容同样可行 |

> **本步是赛题最大不确定项**。给自己设一个硬止损点：如果在计划窗口内 `--ozone-platform=wayland` 一直不通，**立刻并行保底路线**——用已确实跑通的 Xwayland + `--ozone-platform=x11`，先把 10 分窗口分拿到手，再回头攻 Wayland。

```sh

         --disable-dev-shm-usage \
         --window-size=800,600 --window-position=0,0 \
         --disable-features=Translate,BackForwardCache \
         --no-first-run --no-default-browser-check \
         --user-data-dir=/tmp/chromium-profile \

```

**输入**：HTML 文件已在 guest 内；Weston 运行中。
**预期结果**：Chromium 窗口内显示出该 HTML 的内容（标题、文字、色块、边框都符合源文件）。
**验证方式**

#   monitor 里： screendump /tmp/evidence/s11-html.ppm

```

打开 PNG，**逐项对照** HTML 源文件：文字内容、颜色、布局顺序。全部对得上才算"渲染正确"。

**常见问题**

| 现象 | 原因 | 排查方向 |
|---|---|---|
| 窗口出来但白屏 | 页面没加载到 / 渲染路径失败 | 用 `file:///` 绝对路径确认文件存在；试 `about:blank` 是否能出灰底 |
| 提示 profile 目录错误 | `/tmp` 不可用或重复启动 | 加 `--user-data-dir=/tmp/chromium-profile` |
| 中文显示成方块 | guest 内缺字体 | `apk add font-noto-cjk`（体积不小，注意空间）；或测试页用英文 |
| 字体/渲染与主机不同 | 软件渲染与字体差异 | **这是正常的**；判据是"内容与结构正确"，不是"像素级一致" |
| 截图里浏览器窗口被截断 | 窗口大于屏幕几何 | display 契约几何固定，无法改分辨率 → **调小 `--window-size`** |
| 用 `--single-process` 才出画面 | 多进程 IPC 有缺口 | 交付形态必须体现多进程；把缺口登记进清单（中阶任务得分点） |

## 5. 故障排查决策树

```
图形起不来？
├─ QEMU 命令行里没有 virtio-gpu-pci
│   ├─ .config 里 KFEAT_DRIVER_VIRTIO_GPU 没开        → make menuconfig 打开
│   └─ 命令里漏了 GRAPHIC=y                            → 加上
├─ guest 串口里 [weston-start] 报 apk 失败
│   └─ weston 在 community 仓库，rootfs 只开了 main    → S8 启用 community
├─ guest 内 /dev/dri/card0 不存在
│   ├─ 内核日志里 DRM/display 初始化失败               → 看 console.log，make symbolize 定位
│   └─ 内核是旧构建                                     → 重新 make build（改配置后必须重编）
├─ weston 进程起来又退出
│   ├─ /tmp/weston.log 报 no drm device                → 确认 --drm-device=card0 与设备名一致
│   ├─ 报 atomic 相关错误                              → 官方已用 WESTON_DISABLE_ATOMIC=1 兜底；
│   │                                                     去掉它复现失败 → 正是缺口 #2 的复现方法
│   └─ 报 input / libinput 错误                        → /run/udev/data/c13:{1,2} 是否生成（S5/S8）
├─ 起来了但截图黑屏
│   ├─ 截得太早                                         → 延后截图
│   └─ Weston 用的是 pixman 软件后端未 flush            → 看 weston.log 有无 renderer 报错
└─ 总在图形成立前卡住
    └─ 回到 S3（无图形）确认内核/rootfs 本身健康

Chromium 起不来？
├─ 报无法连接 display                → 检查 XDG_RUNTIME_DIR / WAYLAND_DISPLAY（socket 可能叫 wayland-1）
├─ 报 /dev/shm 相关                  → 加 --disable-dev-shm-usage（必加）
├─ 报 sandbox 相关                   → 加 --no-sandbox（必加，上游无 unshare/setns）
├─ 卡 GPU                            → 加 --disable-gpu / --use-gl=swiftshader
├─ 窗口全黑                          → 加 --in-process-gpu
├─ renderer 反复崩                   → 登记为缺口（V8 JIT / memfd sealing）；临时 --single-process 定位
└─ 进程被 Killed                     → 内存不足；提 MEM，查 dmesg，警惕决赛 1.5 GB 资格线
```
