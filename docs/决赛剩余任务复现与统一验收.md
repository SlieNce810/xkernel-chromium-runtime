## 单轮正式页面复现

在 T490 的 `~/xk6` 目录运行。每个 tag 必须唯一；每次 `t490_round.sh` 都会使用新 QEMU 会话，证据保存在新的 `evidence/YYYY-MM-DD_t490-<tag>/` 中。

`scripts/t490/t490_round.sh` 和 `run_session_t490.sh` 支持 `KERNEL_DIR` 指向隔离 worktree，默认仍为 `~/x-kernel`。隔离候选时显式传 `KERNEL_DIR=<worktree>` 与冻结基线 `BASE_IMG=<image>`；启动脚本、构建产物路径和 build-manifest 源码状态都使用同一 worktree，原始冻结目录不需替换。

```bash
cd ~/xk6
unset PLAT_MEM_OVERRIDE
env -u PLAT_MEM_OVERRIDE \
    SCORE_AUTORUN=autorun_mp_score_observe6.sh \
    PROCESS_STRUCTURE_GATE=1 \
    EXTRA_FLAGS_VALUE='--js-flags=--jitless' \
    bash scripts/t490/run_score_page_mp.sh html goal2g-index-cold04 1800 60
```

`platform.env` 默认提供 `MEM=2g`、`SMP=4`、`ACCEL=n`。cold03 使用 `autorun_mp_score_observe6.sh`，由 guest 进程快照产生带 PID/PPID 的 Browser、Zygote、Renderer 事件，外层 `PROCESS_STRUCTURE_GATE=1` 对父链作严格判定；`official-index` 仍独立按像素规则判页。固定启动参数保留 `--ipc-connection-timeout=600`、`--js-flags=--jitless` 与 Wayland；该静态页运行不作为 JavaScript 功能评分。该 observer 的 `--no-sandbox` 仍是诊断模式，不能证明原生 sandbox。正式命令和 Chromium 实际 argv 都保存在 `cmd.txt` 与 console log。

## 统一验收入口

从仓库根目录的 Linux/WSL Bash 运行。`function` 顺序执行 2 GiB HTML、Browser → Zygote → Renderer、双页签、真实输入、JavaScript 和 CSS 六项功能；`all` 还会做本地基线、T490 平台预检、稳定性轮、性能计划和严格 goal audit。稳定性入口默认使用 r10 已通过的 14 guest 秒 family watchdog 目标周期。SSH 目标通过环境变量传入，不把机器地址或密钥写入仓库：

```bash
T490_TARGET=mo@10.249.11.192 bash scripts/final-acceptance.sh function
T490_TARGET=mo@10.249.11.192 bash scripts/final-acceptance.sh all
```

测试隔离候选内核时，用 `T490_KERNEL_DIR` 和 `T490_BASE_IMG` 指定 T490 上的绝对路径；入口会拒绝空格、shell 元字符与 `..` 路径段，并把实际值写入 `env.txt`：

```bash
T490_TARGET=mo@10.249.11.192 \
T490_KERNEL_DIR=/home/mo/xk6/worktrees/xk-compat-fix-r1 \
T490_BASE_IMG=/home/mo/x-kernel/images/pkg-installed.img \
bash scripts/final-acceptance.sh html
```

启动 QEMU 前可先用统一 dry-run 检查 wiring；该模式的 `acceptance.json` 会写明 `dry_run=true`、浏览器分数为 `NOT RUN`，不能用作功能验收结果：

```bash
ACCEPTANCE_DRY_RUN=1 \
ACCEPTANCE_OUT=evidence/$(date +%F)_wsl2-final-acceptance-dryrun \
T490_TARGET=mo@10.249.11.192 \
bash scripts/final-acceptance.sh all
```

`all` 的性能阶段需要 `ACCEPTANCE_PERF_PLAN` 指向 T490 上已有的有效采集计划；缺少计划、内存字段或有效样本时会保留失败状态，goal audit 也会以 `INCOMPLETE` 记录尚未关闭的功能、兼容性和性能项。

## 性能事件与内存样本

正式样本的 `lifecycle-events.jsonl` 使用单调时钟纳秒和 `clock_id`，每条事件关联唯一 `run_id`、`seq`、`event_id`。至少包含：

- `browser_launch_requested`、`browser_main_loop_ready`；
- 同一 navigation 的 `navigation_requested`、`renderer_create_requested`、`renderer_ready`；
- `first_valid_frame` 与严格 `page_verdict`，二者带 navigation、renderer、PID 和 process instance；
- 后续 `screendump_verified`，带截图相对路径、SHA-256、像素 profile 和采样间隔。

`memory-samples.csv` 必须使用相同 `run_id`/`clock_id`，每秒按 Chromium 进程树 PID/进程实例记录 `rss_kb,pss_kb,uss_kb`，从 Browser 进程启动持续到页面严格完成后至少 60 秒。进程开始/结束事件必须能重建当时完整进程树；缺 PID、PID 复用未区分、空字段、零值、采样间隔缺失或页面/截图关联错误都使样本无效。

有效样本保留原调用形式：

```bash
python3 scripts/collect_metrics.py evidence/<run> \
    --run <unique-run-id> --profile official-index \
    --csv evidence/perf/raw.csv \
    --validation-json evidence/perf/<unique-run-id>-validation.json
```

采集器只把完整有效样本写入 CSV；浏览器启动、首个页面帧、截图采样上界、renderer 创建延迟和峰值 RSS/PSS/USS 都分列保存。旧的 marker-only 日志可用于诊断，但不能作为这四项的有效性能样本。

每项优化需要两种可追溯比较：

- `--comparison-kind baseline`：以干净的 `v0.1-first-runnable` tag 为首个可运行版本基线；
- `--comparison-kind parent`：以优化提交的父提交做机制对照。

两种比较都要求 2 GiB、同宿主/CPU/QEMU、同 Chromium/rootfs/overlay/页面/argv/采样方法；before/after 各至少 5 次独立冷启动，`order.csv` 按 before/after 交替。汇总会输出每项原始值、median、min、max、range、median 变化比例和逐对方向一致性。

```bash
python3 scripts/compare_perf.py \
    --before evidence/perf/before.csv --after evidence/perf/after.csv \
    --before-manifest evidence/perf/before-context.json \
    --after-manifest evidence/perf/after-context.json \
    --order evidence/perf/order.csv \
    --comparison-kind parent \
    --out evidence/perf/comparison-parent.json
```

`compare_perf.py` 拒绝 dirty 树、guest 内存不等于 2 GiB、配置不一致、重复 run ID、少于五轮、非交替顺序或未关联父提交的结果。当前 kernel 工作树仍 dirty，因此不能把它用于最终优化结论。
