## 0. 结论先行：三条决定成败的事实

### 事实一：组委会已为 Weston 铺好内核侧的路，路线不需要猜 【实测】

`platforms/kplat-aarch64/qemu_defconfig`（**就是赛题第七节所说的 "qemu_defconfig 基线配置"**，文件真实存在）含如下原文：

```ini
# Weston graphics requires the virtio GPU and input drivers.
KFEAT_DRIVER_VIRTIO_GPU=y
KFEAT_DRIVER_VIRTIO_INPUT=y
```

**含义**：官方意图路线 = **Weston（Wayland 合成器）+ DRM backend + Chromium `--ozone-platform=wayland`**。
注意对比：旧的 `platforms/aarch64-qemu-virt/defconfig` 里这两项是 `is not set`（关闭）。基线是专门为 Weston 调过的。
→ **不要一上来去啃 fbdev 或从零搭 X11**，那是逆着出题意图走。

### 事实二：上游仓库已附带一个"能跑但充满妥协"的 Weston 启动器 【实测】

`uapps/weston-start/` 目录含 `uapp.toml` + `xk-weston-start`（可执行脚本）+ `weston-terminal`。脚本中的关键启动命令原文：

```sh
env XDG_RUNTIME_DIR=/run/user/0 WESTON_DISABLE_ATOMIC=1 weston \
    --backend=drm-backend.so --renderer=pixman --drm-device=card0 \
    --seat=seat0 --continue-without-input --idle-time=0 --xwayland --log=/tmp/weston.log
```

同时脚本还做了两件"绕过内核缺陷"的事：

```sh
# 1) 伪造 udev 数据，骗过 libinput 的设备发现
cat >/run/udev/data/c13:1 <<'EOF'
E:ID_INPUT=1
E:ID_INPUT_MOUSE=1
E:ID_SEAT=seat0
EOF
# 2) 用 seatd 兜底 seat 管理
seatd -g root -l debug >/tmp/seatd.log 2>&1 &
```

**含义**：`WESTON_DISABLE_ATOMIC=1`、`--renderer=pixman`、`--continue-without-input`、伪造 `/run/udev/data` —— **这四个妥协点就是命题方留给你去解决的得分点**，也是你写"系统调用与内核接口缺口清单"时最有分量的素材。

## 2. 赛题理解与需求分析

### 2.1 三层任务的真实含义

| 层级 | 赛题要求 | 真正的技术门槛 | 你的判断 |
|---|---|---|---|
| **基础**（图形环境） | 启动 Weston/其他图形系统，稳定运行 | 内核配置 + rootfs 备好 Weston + DRM 链路通 | **低-中**：官方 `xk-weston-start` 已给出答案，风险主要在环境搭建 |
| **中阶**（浏览器功能） | Chromium 创建窗口 + 渲染指定 HTML + 输入交互 | Chromium 多进程（renderer 子进程）、wl_shm 共享内存、V8 JIT、沙箱 | **高**：**全赛题最大不确定项** |
| **高阶**（跨层优化） | 启动首帧/页面加载/renderer 创建延迟/峰值内存 | 可观测工具 + 跨层定位 | **中-高**：Mo 的性能优化经验可直接迁移 |

| 性能观测与量化方法 | 15 | 中：脚本 + ≥4 类指标 + 5 次取中位数 + 改善数据 | **高** | ★★★ 稳分 |

### 2.3 特别注意："缺证据按项计 0 分"

这是本赛题最"反直觉"的规则——**功能做出来了但没留证据 = 0 分**。所以从一开始就要建立证据纪律：

| 评分项 | 必需证据 | 采集方式 |

## 3. 技术路线选型（含实测现状盘点）

### 3.1 x-kernel 图形与兼容性现状（本次实测结论）

| 组件 | 上游现状 | 证据 | 对赛题的影响 |
|---|---|---|---|
| 内核配置 | 28 项 `KFEAT_*` 可裁剪；基线已开 virtio-gpu/input | `platforms/kplat-aarch64/qemu_defconfig` | 图形驱动**已就绪**，无需从零写 |
| virtio-gpu 驱动 | 已实现（适配 `DisplayDevice` trait） | `drivers/devices/virtio/src/gpu.rs` | 只能 2D scanout |
| virtio-input 驱动 | 已实现（适配 `InputDevice` trait） | `drivers/devices/virtio/src/input.rs` | 输入链路已通 |
| display 契约 | 仅 `info`/`need_flush`/`flush` + 2D scanout resource；**格式只支持 `Bgra8888`**；**无 mode setting / 无 EDID / 无多显示器 / 无 damage track** | `drivers/contracts/display/docs/design.md` | 3D 加速无路；模式固定 |
| **DRM 设备层** | **已实现 `Card0`（驱动名 `simpledrm`）**：legacy ioctl + **atomic KMS 路径** + dumb buffer + page flip + vblank 事件 + poll/mmap，uapi 结构对齐 Linux `drm.h` | `io/drmdevice/{card0.rs, drm.rs, consts.rs}` + `docs/design.md` | **这是最大的意外惊喜**：不用从零写 DRM |
| DRM 局限 | **无 render node、无 GEM execbuf、无 DMA-BUF 跨设备共享、无连接器热插拔** | 同上（Non-Responsibilities 段） | 只能用软件渲染 |
| fbdevice / inputdev | 存在 | `io/fbdevice/src/lib.rs`、`io/inputdev/src/lib.rs` | fbdev 与 evdev 都在 |
| 文件系统 | `9p / anon_inodefs / bpffs / cgroup2fs / devfs / fat / kext4 / memfs / pipefs / procfs` | `fs/filesystems/` | **无 `tmpfs`→ 无 `/dev/shm`；无 `sysfs`** |
| syscall 数量 | 分发表共 **251** 项（Linux aarch64 约 450） | `core/ksyscall/src/dispatch.rs` | 覆盖率约 55%，Chromium 会撞墙 |
| 关键 syscall 已实现 | `epoll_*`、`futex`、`membarrier`、`clone`/`clone3`、`eventfd2`、`timerfd_*`、`signalfd4`、`memfd_create`、`socketpair`、`pidfd_*`、`inotify_init1`、`seccomp`、`statx`、`madvise`、`mprotect`、`sysv shm*` | 同上 | 赛题列的"重点方向"大部分**已有基础** |
| 观测能力 | `ktrace`/`tracepoint`/`eBPF(kBPF)`/`fio`/`iperf3`/`schbench`/`libc-test`；`KFEAT_PMU`、`KFEAT_NMI`、`KFEAT_WATCHDOG` | 仓库结构 + 社区发布说明 | 15 分观测项的**现成基础很好** |
| 许可 | Apache-2.0 | `LICENSE` | 补丁回馈社区无障碍 |

### 3.2 路线对比与推荐

| 路线 | 具体做法 | 工作量 | 风险 | 建议 |
|---|---|---|---|---|
| **A · 原生 Wayland（推荐主路线）** | Weston `drm-backend.so` + `pixman` + Chromium `--ozone-platform=wayland` | 中 | **中**：依赖 wl_shm/memfd/sealing 与 V8 内存语义 | ★★★ **主攻** |
| **B · X11 / Xwayland（推荐兜底）** | 复用 `xk-weston-start` 的 `--xwayland` + Chromium `--ozone-platform=x11` | 中 | 中-高：需要 X server 与 Xwayland 都稳 | ★★ 并行验证，作为 A 失败时的保险 |
| C · fbdev | Weston fbdev backend | 低 | **高**：display 契约明确"无 mode setting"，fbdev 后端对外暴露未确认 | ✗ 不推荐 |
| D · 纯 headless | 不启图形，Chromium headless | 低 | — | ✗ 拿不到图形分，无意义 |

> 注意：`xk-weston-start` 里**已经在跑 xterm/xclock（经 Xwayland）**，说明 B 路线的 Xwayland 链路是通的、被官方验证过的。所以 **A 主 B 备**是低风险组合。

### 3.3 ★ 已识别的技术缺口（初版缺口清单，可直接作为起点）

评分项「缺口清单：每个缺口 1 分，最多 8 个」——下面是我本次实测直接得到的候选，**先记为待复核，再逐个写复现方法**：

| # | 缺口 | 证据 | 影响 | 难度 |
|---|---|---|---|---|
| 1 | **未实现 syscall 返回 `KError::Unsupported`（ENOTSUP）而非 `ENOSYS`** | `dispatch.rs` 末尾 `warn!("Unimplemented syscall"); Err(KError::Unsupported)` | glibc 的 fallback **只认 ENOSYS**；返回 ENOTSUP 会让 glibc 把"不支持"当硬错误，**放弃降级路径** → 系统性兼容性 bug | ★ 小改大收益，**patch 价值最高** |
| 2 | **`WESTON_DISABLE_ATOMIC=1`** | `xk-weston-start` 脚本原文 | atomic KMS 实际不可用或不可靠，只能退回 legacy CRTC，**每帧 ioctl 更多、无原子提交** → 直接影响首帧延迟 | ★★★ 高价值高投入 |
| 3 | **无 udev / uevent / sysfs 设备发现**，需伪造 `/run/udev/data/c13:{1,2}` | `xk-weston-start` 脚本原文 | libinput 无法自动枚举设备；设备热插拔失效 | ★★★ |
| 4 | **`inotify_init1` 只返回 dummy fd** | `dispatch.rs` 的 `sys_dummy_fd` 分组 | inotify **实际不可用**，且缺 `inotify_add_watch`/`rm_watch`；Chromium/glibc/打包工具链会用到 | ★★ |
| 5 | **`rseq` 返回 ENOSYS** | `dispatch.rs`（注释自称 benign） | glibc/V8 的 TLS 与 `getcpu` 快速路径退化 → **性能缺口**（正对"启动首帧/页面加载"指标） | ★★ |
| 6 | **无 `unshare` / `setns`** | `dispatch.rs` 中 0 命中 | Chromium 沙箱不可用，必须 `--no-sandbox`；影响"浏览器进程隔离"扩展方向 | ★★★ |
| 7 | **无 `/dev/shm`（无 tmpfs）** | `fs/filesystems/` 列表 | Chromium 共享内存只能走 memfd 路径；部分组件依赖 `/dev/shm` | ★★ |
| 8 | **无 `sysfs`** | 同上 | 大量用户态工具链（含部分 GPU/桌面组件）依赖 `/sys` | ★★ |
| 9 | dummy fd 组：`userfaultfd` / `io_uring_setup` / `perf_event_open` / `fanotify_init` / `fsopen` / `fspick` / `open_tree` / `memfd_secret` | `dispatch.rs` 原文 | 性能分析工具与容器工具受限 | ★ |
| 10 | 输入路径需 `--continue-without-input` 兜底 | `xk-weston-start` 脚本原文 | 输入设备就绪时序不确定 → 决赛"键盘回显/鼠标点击"4 分有风险 | ★★ |
| 11 | display 契约无 mode enumeration / EDID / 多显示器 | `drivers/contracts/display/docs/design.md` | 分辨率固定；决赛"多窗口/多页签"需在固定几何下实现 | ★★ |
| 12 | 仅 `Bgra8888` 一种 scanout 格式 | 同上 | 格式协商能力缺失 | ★ |

> **使用方式**：这 12 条已是"有据可查"的候选。**每条都要补上"复现方法"才算成立**（评分要求"附复现方法"）。优先把 #1、#4、#5、#9 做成上游可接受的 patch（低风险、边界清晰、易 review），#2、#3 作为技术报告的重点分析。

### 3.4 上游 patch 策略（12 分，周期最长，必须最先启动）

评分：**"一个高质量 patch 被上游合并 4 分，最多计 3 项"=12 分**（决赛阶段另有"开源回馈 9 分"）。

**关键认知**：patch 的 review-merge 周期以**周**计，绝不是最后一周能补的。所以第 1 周就要开始提。

推荐 patch 次序（由易到难，先建立 contributor 信任）：

1. **#1 ENOSYS 语义修复** —— 改动极小、论据极强（glibc 契约）、review 阻力最低。**首选**
2. **#4 补 `inotify_add_watch`/`rm_watch`** —— 功能明确、有测试可写
3. **#5 `rseq` 基础实现或明确降级路径** —— 有性能论据（可附 benchmark）
4. **文档类 patch**（补 `docs/` 下缺文档、修正 `.config` 注释）—— 极低风险，先混脸熟

提交纪律：**先提 issue 描述缺口与复现 → 得到 maintainer 认可再提 PR**，避免 PR 被直接关闭。

## 5. 环境与工具准备

### 5.1 宿主机选择（**先做这个决定，会影响后面所有事**）

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **原生 Linux 真机/虚拟机（Ubuntu 22.04/24.04）** | 构建快、`debugfs` 原生、QEMU 稳定、TCG 性能最好 | 需要一台机器或 VM | ★★★ **强烈推荐** |
| WSL2 on Windows | 复用现有 Windows 环境 | `debugfs`/loop 设备/嵌套虚拟化可能有坑；TCG 纯软件模拟本就很慢，再套一层更慢 | ★ 仅作备选 |
| macOS | — | 交叉工具链与 `debugfs` 麻烦 | ✗ |

> 补充：赛题要求**初赛数据必须出自纯 TCG 软件模拟（禁用 KVM/HVF）**。开发阶段可用加速，但**用于评分的数据必须 TCG**。这意味着**每次完整测量都会很慢**（TCG 下 Chromium 启动可能要分钟级）。→ **宿主机 CPU 单核性能直接决定你的迭代速度**，务必选好机器。

### 5.2 硬件建议

- CPU：高主频、单核强（TCG 是解释执行，单核性能决定一切）
- 内存：≥16 GB（QEMU 建议分配 2–4 GB）
- 磁盘：≥100 GB 可用（rootfs、镜像、多次构建产物、录屏）

### 5.3 工具链安装（照抄即可）

```bash
# 1) Rust + AArch64 裸机 target
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
rustup target add aarch64-unknown-none-softfloat

# 2) QEMU（版本必须 ≥ 8.0）
sudo apt update && sudo apt install -y qemu-system-arm qemu-system

# 3) musl 交叉工具链（aarch64）
curl -LO https://musl.cc/aarch64-linux-musl-cross.tgz
sudo tar -C /opt -xzf aarch64-linux-musl-cross.tgz
echo 'export PATH=/opt/aarch64-linux-musl-cross/bin:$PATH' >> ~/.bashrc && source ~/.bashrc

# 4) rootfs 注入所需（uapps 依赖 debugfs）
sudo apt install -y e2fsprogs

# 5) 观测与调试
sudo apt install -y strace ltrace gdb binutils-dev perl-python \
                    linux-tools-common linux-tools-generic   # perf
```

### 5.4 获取基线并跑通（**阶段 1 的核心动作**）

```bash
git clone https://gitee.com/openkylin/x-kernel.git
cd x-kernel

# 关键：用组委会指定的基线配置
cp platforms/kplat-aarch64/qemu_defconfig .config
make defconfig

# rootfs
make rootfs ROOTFS_VARIANT=alpine-busybox

# 注入 uapps（含 weston-start）
make uapps

# 构建 & 运行
make build
make run
```

进阶参数（QEMU 侧）：

```bash
# 显式指定虚拟设备组合，对齐赛题第七节要求
make run XKMAKE_ARGS='--memory 4g --smp 4'

# 打开 guest_errors 便于定位设备问题
make run XKMAKE_ARGS='-- --d guest_errors'
```

## 10. 观测与测试方案设计（对应 15 分，建议原样落地）

### 10.1 一键测量脚本的必备能力

| 能力 | 要求 | 对应得分 |
|---|---|---|
| 一键运行 | `bash scripts/measure-all.sh` 无参数即可跑完 | 可复现 5 分 |
| 指标覆盖 | ≥4 类（启动首帧/页面加载/renderer 创建/峰值内存/CPU） | 覆盖 4 分 |
| 统计规范 | 每项 ≥5 次，取中位数 + 波动范围 | 规范 3 分 |
| before/after | 相对冻结 tag 的改善百分比自动计算 | 改善 3 分 |
| 环境指纹 | 自动记录宿主机 CPU/内存/QEMU 版本/OS | 交叉核验必需 |
| 原始数据 | 每次运行落盘 CSV，不覆盖 | 赛题要求提交原始数据 |

### 10.2 建议目录结构

```
evidence/<date>_<tag>/
├── env.txt            # uname -a, qemu --version, lscpu, free -h
├── run01/ ... run05/  # 每次运行的 log + 时间戳
├── raw.csv            # 汇总原始数据
├── summary.md         # 中位数 + 波动范围 + 对比
└── screenshots/       # screendump 产物
```

### 10.3 观测手段优先级

1. **时间戳插桩法**（最稳）：在脚本中用 `date +%s.%N` 打点，不依赖 guest 工具
2. **串口日志时间戳**：内核日志带时间，可定位内核侧耗时
3. **`ktrace` / `tracepoint` / `kBPF`**：x-kernel 自带的观测设施（社区已有 fio/iperf3/schbench 等基线）
4. **`strace`**（若能装进 guest）：定位 syscall 级失败
5. **宿主机 `perf`**：只能看 QEMU 进程整体，粗粒度
