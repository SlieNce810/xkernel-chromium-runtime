## Chromium 页面渲染闭环 · 阶段零侦察 + 阶段一/二首轮

### 新确立的硬事实（都有证据文件）
- **`Failed to initialize cpuinfo` 是 zygote 打的**，`__FILE__:line` = `content/app/content_main_runner_impl.cc:414`，
  且 `[91:91]`（tid==pid，单线程刚 fork）→ 接着才 `zygote_main_linux.cc:202 ZygoteMain`。
  **不是 fatal**：zygote 会继续跑到 ZygoteMain；但 zygote 与 browser 随后都静默消失。
- **⚠️ 纠错（上游源码核实后推翻）**：`Failed to initialize cpuinfo` **完全不致命**。Chromium
  `content/app/content_main_runner_impl.cc` 的 `PreSandboxInit()` 里是
  `#if BUILDFLAG(BUILD_TFLITE_WITH_XNNPACK) if (!cpuinfo_initialize()) { LOG(ERROR) << "Failed to initialize cpuinfo"; } #endif`
  —— **只有一条 LOG，没有 return/FATAL**（这也解释了 zygote 打完它还能走到 ZygoteMain）。
  所以 cpuinfo / `/proc/sys/fs/inotify` 都是**接口完整性修正**，不是 renderer 的阻塞点。
- **接口缺口本身仍成立**：ARM64 Linux 上 `cpuinfo_arm_linux_init()` 首道门是
  `max_present = 1+parse(/sys/devices/system/cpu/present)`、`max_possible = 1+parse(/sys/.../possible)`，
  `if ((max_present|max_possible)==0) { log_error; return; }` → `cpuinfo_is_initialized` 永不置 true。
  **x-kernel 根本没有 sysfs**（`fs/filesystems/` 无 sysfs 实现，`/sys` 只是 rootfs 普通目录）⇒ present/possible 必然缺失。
  `/proc/cpuinfo` 是并列的第二道门（`parse_proc_cpuinfo` 失败也 return）。
- **结论纠错**：之前 report/18 把 `--use-gl` 当变量、把 cpuinfo 当唯一疑点都不对。实测去掉 `--disable-gpu` 后
  `gl=none` **依旧**（`--use-gl=swiftshader` 在本 build 的 allowed 列表里不存在，列表只有 egl-angle+{opengl,opengles,vulkan}）。
- **fullbase 轮（commit 7f77919）实测**：browser pid=141 存活至 02:31:29 打最后一行日志，
  **02:32:16 退出 rc=191**；zygote 179/181 在 t=30s 前已消失；**`type=renderer` 出现次数 0**；
  `FileURLLoader::Start: file:///usr/share/html-test/index.html` 有发生。
- **坑**：`run-session.py` 判活用 `kill -0 $CPID`，**僵尸进程也算活** → 必须同时看 `/proc` 进程快照。
- **坑**：guest `/root/*.log` 不在宿主上，但 `disk.img` 留在宿主 → 用
  `debugfs -R "dump /root/chrome-full.log /tmp/gl/x" ~/x-kernel/disk.img` 取回。
- **坑**：本机 bash 管道里 `tail` 缺 coreutils → 给**整条**命令（含管道）都加 PortableGit PATH，否则命令"失败"但远端其实已跑完。

## 阶段 A 已执行完毕（report/21）—— 四轮三元组定标

### 结论（详见 report/21 §0）
1. **GL 门禁被打开**：`--use-gl=angle --use-angle=vulkan`（+`VK_ICD_FILENAMES`）是本 build **唯一被接受**
   的 GL 实现 —— `not found in allowed implementations` 与 `gl=none` 双归零，ANGLE Vulkan 跑到
   `ChoosePhysicalDevice`（`angle_platform_impl.cc:52`）。
2. **`--use-angle=opengles` 被拒**（落到 `(gl=none,angle=none)`，与历史 `--use-gl=swiftshader` 同形态）。
   原因是**旗标词汇表不匹配**：allowed 列表打印的是 ANGLE 内部显示类型名，CLI 取值应是
   `gl/gles/vulkan` ⇒ 备选组要改 `--use-angle=gles`。
3. **`GPU_MODEL=separate` 优于 `--in-process-gpu`**：只有 C3 真正出现 `type=gpu-process`

## 22:50–23:20 · 🎯 **突破：找到并修掉真正的根因，Weston 首次真实首帧（无 shim）**

### 根因：「缺口 A 的修复」本身是误修（**第二个误修**，与缺口 D 同类）
- 权威编号（**guest 自带 uapi 头 `drm.h:1159-1164` 逐行核对**）：
  `0xA8`=ATTACHMODE(deprecated)｜`0xAA`=**GETPROPERTY**｜`0xAB`=SETPROPERTY｜`0xAC`=**GETPROPBLOB**
  ⇒ **内核 HEAD 原始值（0xAA/0xAC）本来就是 uapi 值**；p2 的 `0xAA→0xA8`、`0xAC→0xAA` 把两个正确编号改坏了
- **决定性证据链**（每一环都有机器输出）：
  1. `proptwostage.c`：手写两段式 call#1/call#2 全通，**真实 libdrm `drmModeGetProperty` 12/12 失败 errno=95**
  2. `iocspy.c`（LD_PRELOAD 只观测）抓到 libdrm 实际发的是 **`req=0xc04064aa`（nr=0xAA, size=64）**，
     而改坏后的内核只认 `0xc04064a8` ⇒ 未命中分派
  3. `weston_sim.c`（用真实 libdrm 复现 Weston 的 plane 创建）：**12 个属性全部读不到名字**
     ⇒ `plane->type = COUNT` ⇒ `drm_plane_create()` **静默丢弃**（`create_sprites()` 裸 continue）
     ⇒ `Failed to find primary plane`
- 回退：`p2_revert.sh`（恢复 0xAA/0xAC）→ `card0.rs` 与 HEAD **逐字节一致**；内核 `a24ae553` → **`398923f0`**
