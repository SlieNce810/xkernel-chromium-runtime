## ★★★ 追加（13:55）：G4 根因定位到源码级 + P1 补丁已实现并编译通过

### G4 根因（铁证，不需要探针也能定性）
**x-kernel 的 AF_UNIX `SOCK_STREAM` 传输层根本没有实现 ancillary（SCM_RIGHTS）的收发。**

```
grep -rc ancillary net/knet/src/unix/stream.rs          → 0
grep -rc ancillary net/knet/src/unix/stream/channel.rs  → 0
grep -rc ancillary net/knet/src/unix/stream/listener.rs → 0
grep -rc ancillary net/knet/src/unix/dgram.rs           → 5   ← dgram 有实现
```

链路逐段核查（全部正确的部分）：
1. `posix/net/src/io.rs::parse_send_cmsgs()` → `CMsg::parse()`：从**发送方** fd 表取
   `Vec<Arc<VfsFile>>`，正确（`resources.get_file(fd)`）。
2. `push_socket_cmsg()`：接收侧 `resources.add_file(f, false)` 装进**接收方** fd 表并回写 fd 号，正确。
3. `recv_impl()`：`socket.recv(..., ancillary: Some(&mut ancillary))` 收 cmsg → `into_socket_ancillary`
   → `push_socket_cmsg` 写入用户缓冲，正确。
4. **但 `StreamTransport::send()` / `recv()` 里 `options.ancillary` 从未被读写** →
   `CMsg::Rights{fds}` 被静默丢弃、接收侧 `Vec` 永远为空 → `msg_controllen=0`
   → libwayland 报 `file descriptor expected, object (10), message create_pool(nhi)`。

**结论：不是 cmsg 解析问题，也不是 libc/用户态问题；Wayland 走 SOCK_STREAM，所以 fd 全丢。**

## ★★★ 追加（15:55）：P2 补丁（sched tid + netlink groups）已实现并**用探针直接验证通过**

### 根因修正：两处都是**行为缺陷**，不是缺功能
| 项 | 落点 | 缺陷 |
|---|---|---|
| sched | `core/ksyscall/src/task/sched.rs::scheduler_target()` | 只调 `kprocess::scheduler::target_task(pid)`，而它是"按 **tgid** 查进程再取代表线程"。musl 的 `pthread_getschedparam` 传的是**目标线程的内核 tid** → 非主线程调用必然 ESRCH(3)。同文件 `affinity_target()` **已经**做了 tid 优先+进程回退（注释还写着 Linux 接受 tid），`scheduler_target` 没有 |
| netlink | `net/knet/src/netlink/socket.rs::bind()` | `NETLINK_ROUTE && addr.groups != 0` 直接 `return Err(EOPNOTSUPP)`。Chromium `AddressTrackerLinux` 无条件用 `nl_groups` 订阅 → bind 失败 |

### 补丁（`scripts/t490/p2_sched_netlink.py`，+37/+13，`make build` 通过）
- `scheduler_target()` 改为 **tid 优先（`task_by_tid`）+ 进程回退（`target_task`）**，与 `affinity_target` 一致；
  另加 2 个单测（caller/自身 tid 能解析、非法 id 返回 ESRCH）。
- `NetlinkSocket::bind()` **接受** `groups != 0`，照常记录到 `local_addr`；
  组播投递目前只有 kobject-uevent 一条通路 → RTMGRP_* 订阅者暂时收不到通知，
  在静态网络配置的 VM 里等价于"路由表从不变化"，已按 TODO 注明。

## ★★★ 追加（16:45）：P3 —— 找到并修好**所有 Chromium 子进程全灭**的真正根因

### 根因（源码级铁证，两段对上）
Chromium `base/process/launch_posix.cc` 在 **fork 之后、execvp 之前**执行：

```cpp
    if (!options.allow_new_privs) {
      if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)) {
        // EINVAL→内核<3.5 不支持；EPERM→环境限制（如系统强加 seccomp）
        if (errno != EINVAL && errno != EPERM) {
          RAW_LOG(FATAL, "prctl(PR_SET_NO_NEW_PRIVS) failed");   // ← 子进程 abort
        }
      }
    }
```
x-kernel `core/ksyscall/src/task/ctl.rs` 对该 option **无条件返回 ENOSYS(38)**（连 `_ =>` 都没走到，
是专门写的一臂 + 单测 `prctl_set_no_new_privs_requires_exec_enforcement` 固化）。
**38 既不是 22 也不是 1 → 命中 RAW_LOG(FATAL)。**

### 这一条链一次解释掉全部"矛盾"
| 现象 | 解释 |
|---|---|
| 子进程**零输出**（日志只有 browser PID） | 死在 `execvp()` 之前，目标程序从未加载 |
| 那行 `prctl(...) failed` **没有 `[pid:tid:…]` 前缀** | RAW_LOG 在 fork 后直接写共享 stderr |
| `--single-process` 恒 **rc=191** | 子进程初始化跑在 browser 内，撞同一条 FATAL |
| `childprobe` 全绿却仍无 renderer | 探针没调这个 prctl，正好绕过唯一坏掉的一步 |

### 补丁（1 文件 / +20 行，`scripts/t490/p3_prctl_nonewprivs.py`）
`PR_SET_NO_NEW_PRIVS` 改为 `kprocess::current_user_thread().set_no_new_privileges();`（落到 `Ok(0)`）。
- `set_no_new_privileges()` **早已存在**（`process/kprocess/src/thread/core.rs`），
  且 `prepare_process_fork` / `prepare_thread_clone` **都已**做 fork/clone 继承 → 真语义，不是桩
