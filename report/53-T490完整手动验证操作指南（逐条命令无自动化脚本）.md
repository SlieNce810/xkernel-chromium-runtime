# 53 · T490 完整手动验证操作指南（逐条命令，无自动化脚本）

整理日期：2026-10-09。本文是待执行的操作指南，不是新一轮实测报告。

本流程基于仓库现有 Weston / Wayland / Chromium 单进程实现：检查环境 → 制作独立工作盘 → 手动启动 guest 服务 → 验证首页及 10 分钟稳定性 → 验证交互和布局 → 核查多进程边界 → 回收、校验证据。需要性能复测时，再独立重复五轮。

**不运行仓库中的 `.sh`、`.py`，不使用 `source platform.env`、`python -c`、循环、函数或自动化测试驱动，也不调用 `make run` 间接启动流程。** 每条命令在交互终端手动执行。变量、管道、重定向是命令行用法，不是另写脚本。guest 正常登录初始化和被测 HTML 内置的 JavaScript 属于系统/被测对象；本文不使用 `?e2e=1` 触发自动输入，不向网页注入 JS。

**当前证据边界：** 历史归档证明单进程页面渲染与稳定性；真实 virtio-input 事件消费、独立 renderer / zygote 仍有缺口。一次“完整验证”应把这些项实际检查并记录 PASS / FAIL / BLOCKED，不能预先承诺全部通过。

**前提：** T490 已有 `/home/mo/xk6`、`/home/mo/x-kernel`、已构建的内核、基础镜像和 p31 overlay。本文验证既有产物，不从零构建内核。缺少这些产物应停止准备阶段；不要自动换成上游 HEAD 或其他镜像。本流程不证明源码构建可复现，源码状态与二进制来源需要各自留档。

**1．登录并确认机器**

在 T490 物理机终端操作可直接从 `hostname` 开始。远程操作时，Windows PowerShell 先执行：

```powershell
ssh -i "$env:USERPROFILE\.ssh\id_ed25519_t490" mo@192.168.1.217
```

目的：连接历史记录中的 T490。正常：出现 `mo` 的 Linux shell；首次主机密钥提示需与该机器核对。异常：超时是地址/网络问题，`Permission denied` 是账户/密钥问题。地址来自历史记录，并非本次在线确认；若机器换了 IP，使用 T490 当前地址。

**5．直接启动 QEMU**

在 T490 物理桌面的 H1 使用 `-display gtk`。纯 SSH、没有桌面显示变量时，把这一项改为 `-display none`，保留 GPU、串口和 monitor，后面用 screendump 看图。不要为 SSH 盲设 `DISPLAY=:0`。

先执行 `cd "$E"`：使 monitor 使用相对路径时把截图写入本轮目录。正常无输出。

再执行下面这一条完整命令；反斜杠是续行，同一条命令全部输入后才执行：

```bash
qemu-system-aarch64 \
  -name t490-manual-r1 \
  -accel tcg \
  -machine virt,gic-version=3 \
  -cpu cortex-a76 \
  -m 2g \
  -smp 4 \
  -kernel "$E/kernel.bin" \
  -device virtio-blk-pci,drive=disk0 \
  -drive "id=disk0,if=none,format=raw,file=$WORK/disk.img" \
  -device virtio-net-pci,netdev=net0 \
  -netdev user,id=net0 \
  -device virtio-gpu-pci \
  -vga none \
  -device virtio-keyboard-pci \
  -device virtio-mouse-pci \
  -object rng-random,id=host_rng0 \
  -device virtio-rng-pci,rng=host_rng0 \
  -display gtk \
  -chardev "stdio,id=console,mux=on,signal=off,logfile=$E/console.log" \
  -serial chardev:console \
  -mon chardev=console,mode=readline \
  -pidfile "$E/qemu.pid" \
  2> "$E/qemu.stderr"
```

目的：用明确的 TCG、AArch64 virt、2 GiB、4 vCPU 和四类 virtio 设备启动固定内核/工作盘，并让 QEMU 自身记录串口/monitor 输出。使用显式 chardev 是为了原生命令行留日志；不要再额外加 `-serial mon:stdio` 或 `-nographic` 抢同一个 stdio。这里不需要旧轮次的 61005/61006 端口映射。

正常：H1 出现 x-kernel 启动日志，随后出现 guest shell；gtk 后端会出现 QEMU 窗口。Weston 尚未启动时黑屏或显示输出未激活正常。

异常：命令立即返回，先在 H1 执行 `cat "$E/qemu.stderr"`。`gtk initialization failed` 表示显示后端问题；`Failed to get write lock` 表示镜像被占用；`Could not load kernel` 是路径/产物问题。**失败轮保留，修正后用新轮次重启，不能覆盖 console.log。** 内核 panic、不断重启、始终无 shell 则属于启动失败，不能继续宣称图形验证完成。

TCG 判据是实际选择 `-accel tcg`，不是“命令行不能有 -accel”。原仓库校验器将所有 `-accel` 都拒绝，是旧工具的约定，不是 QEMU 的真实含义。本手动流程不调用该校验器。QEMU 日志和 monitor 参数语法依据 [QEMU Invocation](https://www.qemu.org/docs/master/system/invocation.html)。

**13．独立 renderer、多窗口/多页面检查（范围完整性）**

单进程模式的 `ps` 不出现独立 renderer 是参数决定的正常结果。不能据此宣称多进程支持通过。若本次范围包含完整浏览器能力，需补做这一项；其失败不回溯抹掉前面已取证的单进程结果。

先 G 正常终止当前单进程 Chromium并用 `ps` 确认退出。然后执行：

```sh

```

目的：去掉 `--single-process --no-zygote`，检查常规 zygote/renderer 路径，GPU 暂保留进程内。正常应有 browser、zygote、renderer 等进程关系和正确页面；不要求进程名完全一致，以 cmdline 与 PPid 为准。紧接着 `MP_PID=$!` 保存 PID。

M 执行 `screendump screenshots/multiprocess-check.ppm` 保存该场景画面。未正确渲染时，本项不能 PASS。若该项失败，勿继续声称多窗口/标签页已通过。

2. 实际发出 G 启动命令。首次人工看到完整正确页时再 H2 执行 `date +%s`，同时 M screendump。
3. 两个宿主时间相减得到“人工首帧观察时延上界”，包含人工输入/看图延迟。它**不是**历史 `FileURLLoader::Start` 或自动首帧指标，报告中须用这个名称。
4. 若测内存，G 在相同观察点执行 `cat /proc/$CHROME_PID/status`，记录 VmRSS；H2 执行 `ps -p "$QPID" -o pid,rss,%cpu,etime`，记录宿主 QEMU。guest VmRSS 与宿主 QEMU RSS 分开列，字段缺失写 N/A，不填 0。
5. 需要评估持续稳定性时，每一轮均另做 ≥600 s 区间；短时性能轮不能继承另一轮的稳定性时长。

在独立性能汇总目录中，用 `printf '%s\n' 实测值1 实测值2 实测值3 实测值4 实测值5 > first-frame-observed.txt` 逐个填入实际秒数，目的为保存五个测量值；不能把占位符当命令值。`sort -n first-frame-observed.txt > first-frame-sorted.txt` 得到有序样本；`head -n 1 first-frame-sorted.txt` 查看最小值；`head -n 3 first-frame-sorted.txt | tail -n 1` 查看 5 次样本的中位数；`tail -n 1 first-frame-sorted.txt` 查看最大值。每条正常输出对应数值，无需 Python/awk 脚本。原始样本和轮次路径必须保留。若某轮失败，不把它无声丢掉后报告“五轮全过”。

只有相同指标定义、相同宿主/运行参数、各至少五轮的 before/after 才可做性能改善对比。缺少基线、原始数据或一致测量口径，就写“未验证性能改善”。本指南不生成 perf/eBPF/火焰图结果。

| 层级 | 必须满足的事实 | 可写的结论 |
|---|---|---|
