## 0. 结论先行

### 0.1 本次核对新发现的硬缺口（最重要）

赛题第七节（一）3 明确要求设备组合包含 **`virtio-input`**。
但 `make run GRAPHIC=y` 生成的命令行里**根本没有 virtio-input 设备**：

```bash
# 取证方法（可复现）
curl -s https://gitee.com/openkylin/x-kernel/raw/main/xtask/xkmake/src/qemu.rs \
  | grep -cE 'input|keyboard|mouse|tablet'
# 输出: 0
```

`add_devices()` 只添加 `virtio-blk-pci` / `virtio-net-pci` / `virtio-gpu-pci` /
`vhost-vsock-pci` / `virtio-rng-pci` 五类，**没有任何输入设备**。

旁证：官方 `xk-weston-start` 给 weston 传了 `--continue-without-input`——
这个参数存在的意义正是"没有输入设备也继续启动"。

| 影响 | 说明 |
|---|---|
| 基础任务 40 分 | **不受影响**（图形 + 渲染照常） |
| 决赛「键盘输入回显与鼠标点击跳转」4 分 | **拿不到** |
| 中阶任务「可根据方案实现输入交互」 | 需先补齐设备 |
| 第五阶「输入事件路径优化」 | 无输入可优化 |

**修复**：把输入设备作为 `QEMU_ARGS` 显式加上（内核侧 `KFEAT_DRIVER_VIRTIO_INPUT=y`
基线已开，**不需要改内核**）：

```bash
make run GRAPHIC=y ACCEL=n MEM=4g SMP=4 \
  QEMU_ARGS='-device virtio-keyboard-pci -device virtio-mouse-pci'
```

`scripts/run-session.py` 已加 `--with-input` 开关，自动完成拼装并保证不会被拆成两个 argv。

> **这条要写进缺口清单**，且它是"环境配置/命令行缺项"类缺口，与内核 syscall 缺口
> 属于不同类别——按评分标准「整理系统调用与内核接口缺口」它不直接计分，
> 但作为「与 Linux 行为基线的对比分析 5 分」的素材很有分量：
> **Linux 下 QEMU 的标准用法会把 gpu 与 input 一起给出，而这里的工具链只给了 gpu。**

## 1. 逐条合规核对矩阵

### 1.1 第七节（一）统一评测平台

#### 条款 1 · 架构与配置

> 统一采用 AArch64 QEMU 虚拟平台（x-kernel kplat-aarch64 平台及组委会发布的
> qemu_defconfig 基线配置），不接受其他架构平台参赛。

| 项 | 内容 |
|---|---|
| **要求拆解** | ① guest 必须是 AArch64；② 必须用 `kplat-aarch64` 平台；③ 必须用组委会发布的 `qemu_defconfig`；④ 不接受其他架构 |
| **现状** | ✅ 满足。手册 S2 强制 `cp platforms/kplat-aarch64/qemu_defconfig .config`；该文件已确认存在且与上游 main 逐字节一致 |
| **证据** | `<证据目录>/cmd.txt`（含 `--dry-run` 打印的完整命令，应为 `-machine virt,gic-version=3 -cpu cortex-a76 -kernel <bin>`）；`env.txt`（宿主架构） |
| **验证命令** | ```grep -E 'qemu-system-(aarch64|riscv64|x86_64)' <证据>/cmd.txt``` → 必须是 `qemu-system-aarch64` |
| **⚠️ 注意** | 赛题说"不接受其他架构"，但**允许用其他架构做开发期快速验证**。风险在于：x86_64 平台跑得更快，容易不知不觉用 x86_64 出数据。**建议在证据目录里落一份 `env.txt` 作硬锚点** |

#### 条款 2 · QEMU 规格

> qemu-system-aarch64 版本不低于 8.0。全部评分数据必须出自纯 TCG 软件模拟环境，
> 初赛阶段统一禁用 KVM/HVF 等硬件加速；开发调试阶段可使用加速，但相关数据不作为评分依据。

| 项 | 内容 |
|---|---|
| **要求拆解** | ① QEMU ≥ 8.0；② 评分数据必须纯 TCG；③ 开发期可用加速但不可作评分依据 |
| **现状** | ✅ 满足。`scripts/env-check.sh` 解析版本号并在 <8.0 时计 FAIL；手册 S0 把版本达标设为硬门禁 |
| **纯 TCG 的实现** | 双重保障：① `ACCEL=n` → xkmake 加 `--no-accel` → 不生成 `-accel`；② `hardware_accel()` 仅在宿主架构 == guest 架构且非 WSL 且 `/dev/kvm` 存在时才返回后端名，**x86_64 宿主跑 aarch64 guest 时天然返回 None** |
| **证据** | `env.txt`（QEMU 版本 + 宿主架构）、`cmd.txt`（完整命令） |
| **验证命令** | ```grep -Eo '\-accel [a-z0-9,=]+' <证据>/cmd.txt``` → **应无输出** |
| **建议固化** | 把上面这条 grep 做成证据归档时的自动校验（见 §5 行动项 A3） |

> **一个容易误判的点**：`-accel tcg` 显式出现也**不算违规**（tcg 就是软件模拟），
> 真正要排除的是 `-accel kvm` / `-accel hvf`。校验时按此区分。

## 2. 四个性能指标的界定与采集方案（我方建议稿）

赛题只给了指标**名称**，没给**定义**。以下是建议口径，用于自测工具设计；
**决赛以组委会脚本为准**，届时需对齐。

| 指标 | 建议定义（起止点） | 主采集点 | 采集方式 | 歧义 |
|---|---|---|---|---|
| **启动首帧** | QEMU 进程启动（`exec` 成功）→ guest 首次上屏非黑画面 | 主机侧 | 主机打点 + monitor `screendump` 轮询（首次 `ppm2png.py` 报非 blank 即视为首帧） | "首帧"指内核 console 首帧、还是图形会话首帧？建议取**图形会话首帧** |
| **页面加载** | Chromium 进程启动 → 页面首个完整帧上屏 | 主机 + guest | 主机打点 + `screendump` 轮询至目标页面特征出现 | 冷启动还是热启动？建议统一冷启动（每次清 `--user-data-dir`） |
| **renderer 创建延迟** | browser 主进程出现 → 第一个 renderer 子进程出现 | guest 侧 | guest 内轮询 `ps` / `/proc/*/stat` 或 `/proc/<pid>/task`，记录首个 renderer PID 出现时刻 | "出现"以进程创建还是以完成初始化为准？建议**进程创建** |
| **峰值内存** | 会话全程的内存上界 | guest + 主机 | guest：轮询 `/proc/meminfo` 的 `MemTotal - MemFree`（或所有进程 RSS 之和）；主机：轮询 QEMU 进程 RSS | **口径未定**：guest 内进程 RSS 之和 vs QEMU 进程 RSS，差异巨大（含 QEMU 自身开销）。**必须向组委会确认** |
| **CPU 使用率**（第 5 类，可得 4 分档） | 会话期间宿主机 QEMU 进程 CPU% | 主机侧 | 主机读 `/proc/<qemu_pid>/stat` | — |

**时间点采集原则**：优先用**主机侧 `date +%s.%N` 打点**，不依赖 guest 内工具是否存在
（guest 是精简 rootfs，计时工具未必齐）。已确认 guest 内 `date` 可用（`xk-weston-start` 自己就在用）。

**首次上屏判定**：`scripts/ppm2png.py` 已内置空白检测（`likely_blank`，基于采样均值亮度），
可直接用于"非黑帧"判定，无需额外图像库。

## 3. 测量协议（≥5 次 + 噪声控制）

建议直接把下面这套写进 `report/性能报告.md` 的"测量方法"章节 ——
**这是「测量脚本与流程可复现 5 分」+「数据统计规范 3 分」的直接得分点**，
也正好复用你在 OC9 已成熟的测量纪律。

### 3.1 每次运行的规程

| 项 | 规定 | 理由 |
|---|---|---|
| 冷启动 | 每次测量都是全新 QEMU 进程，不复用 | 排除状态残留 |
| 序列化 | **同一时刻只跑一个 QEMU**，禁止并发 | TCG 单核打满，并发会互相抢核 |
| 内存规格 | 固定 `MEM=`、固定 `SMP=` | 变更即不可比 |
| 镜像固定 | 用冻结镜像 + 记录 sha256 | 装包导致的镜像漂移会毁掉可比性 |
| 预热 | 至少 1 次预热运行**不计入**统计 | 首次运行含 page cache 冷启动 |
| 采样次数 | ≥5 次，**建议 7 次** | 7 次可去极值后取中位数，更稳 |
| 环境门禁 | 运行前记录 `loadavg`，超阈值则作废重来 | 见 3.2 |
| 原始数据 | 每次落盘独立目录，**永不覆盖** | 赛题要求提交原始数据 |

### 3.2 噪声门控（建议写进报告）

| 门控 | 阈值 | 依据 |
|---|---|---|
| 起始 `loadavg(1min)` | ≤ 0.7 | 与你在物理机测试协议里用的口径一致 |
| 变异系数 CV | ≤ 3% | 超过则判定该批数据不可用，需重测 |
| 极差/中位数 | ≤ 10% | 粗判是否存在离群 |

> 如果某指标天然抖动大（TCG 下很可能），就把 CV 门控放宽并**在报告里显式说明放宽理由**
> ——评委看的是"你是否知道自己在测量什么"，而不是"数据是否完美"。

### 7.1 缺口分类（按赛题评分口径）
- **内核接口/系统调用类**：G3（ioctl 参数语义）、G4（SCM_RIGHTS 跨进程 fd 语义）
- **内核子系统缺失类**：G1 的 sysfs/uevent、G2 的 VT（`/dev/tty0` + procfs tty 信息）
- **工具链/环境配置类**：G5

### 7.2 与 Linux 行为基线的差异（「对比分析 5 分」素材）
1. Linux 侧 `DRM_IOCTL_VERSION` 明确允许 `name=NULL/name_len=0` 只取长度；x-kernel 原实现无条件 copy → **语义差异已修**
2. Linux `seatd` 依赖 VT 激活是标准设计；x-kernel 未提供 VT → 需要 shim 或补齐 `/dev/tty0` 与 VT ioctl
3. Linux 通过 sysfs/uevent 描述设备树；x-kernel 无 sysfs → libudev 无法工作（本处用用户态伪造替代）
4. wayland 客户端与 compositor 依赖 SCM_RIGHTS 传 fd；x-kernel 有收发实现但场景内失败 → **待定位（G4）**

### 7.3 补丁优先级（与 `report/补丁实施计划-P0-DRM版本修复-P1-最小sysfs.md` 一致）
1. **P0 ✅ 完成**：`io/drmdevice/src/card0.rs` 的 NULL 指针处理（commit `8162e8a`）
2. **P1 待推进**：最小 sysfs（`/sys/class/drm/*` + `/sys/dev/char/*`）——当前用运行时伪造过渡，
   正式做法应为内核侧 sysfs 节点（x-kernel 已有 `memfs::SYSFS_TYPE`，可挂载期填充）
3. **P2**：`/dev/tty0` + procfs tty 字段 → 打通 seatd 原生路径
4. **P3（新增，最高业务价值）**：定位/修复 **G4 SCM_RIGHTS** → 打通 wayland 客户端链路
