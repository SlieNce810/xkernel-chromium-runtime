# SCM_RIGHTS 首字节交付候选补丁与 T490 AArch64 流回归（2026-11-19）

## 结论

report 332 的 2 GiB AArch64 guest probe 复现了 Linux 兼容差异：`SCM_RIGHTS` 没有随首个 1-byte `recvmsg` 交付，后续又被报告。候选补丁现在在隔离的 `b73e581` + 53 个既有源码改动快照中通过 `knet::unix::stream` 的 AArch64 QEMU 单测，24/24 PASS，其中包含首读 ancillary 到达、后续读取不重复的回归用例。

随后同源 C guest probe 已在该候选内核上通过 6/6，详情见 [report 334](334-SCM_RIGHTS修复版guest短读复测-20261119.md)。Chromium Mojo 回归仍未完成，因此兼容性矩阵的端到端 SCM_RIGHTS 项尚未最终关闭。原始 x-kernel 目录未被改动。

## 修复

`net/knet/src/unix/stream.rs` 的现有 stream 边界逻辑等到 `bytes_remaining == 0` 才从队列移除并移交 ancillary，因此 100-byte sendmsg 被拆为多个 1-byte recvmsg 时，fd 到得太晚。候选改动在第一次成功消耗该边界任意字节时 `take()` control data；边界剩余字节数继续递减，队列条目仍在剩余数据读完后才移除，因此控制数据只交付一次，字节边界继续保留。

同一个现有诊断钩子 `trace_chromium_stream_frame()` 之前无条件调用 `current_user_process()`；kernel task 进入 stream send 会 panic。候选把它改为 `try_current_user_process()`，无用户进程时直接跳过诊断记录。这是运行 kernel 单测所需的旁路保护，不改变 Chromium 用户进程的 tracing 条件。

可应用补丁见 [scm-rights-first-byte.patch](../patches/compat/scm-rights-first-byte.patch)。该补丁依赖 report 332 记录的冻结 dirty stream 源码，不能视作对干净 `b73e581` 的独立补丁。另一个单测构建准备补丁 [procfs-status-test-signature.patch](../patches/compat/procfs-status-test-signature.patch) 补齐了既有 procfs `format_task_status()` 单测的旧参数表，使 `UNITTEST=y` 能完成依赖编译；它不更改 procfs 产品行为，也不实现 PSS/USS。

## 复现与 Linux 对照

Linux WSL2 与 T490 native Linux 的 6/6 基线见 [report 328](328-SCM_RIGHTS-stream-shortread-WSL2-Linux基线与T490待补-20261119.md) 和 [report 331](331-T490-native-Linux-compat-memory-reference-20261119.md)：fd 随首个字节交付，后续读取不重复，100-byte payload 完整。原冻结 x-kernel guest 的失败日志见 [compat-memory r1](../evidence/2026-11-19_t490-acceptance-compat-memory-r1/console.log)；同一 C 复现程序和输入没有改变。

## 回归结果

成功轮使用 T490 x86_64 / QEMU 10.2.1，guest AArch64，纯 TCG、2 GiB、4 vCPU、virtio GPU/input/block/network。目标过滤器是 `UNITTEST_CRATE=knet::unix::stream`，日志显示 24 tests、24 passed、0 failed、0 ignored，最终 `UNITTEST_STATUS: ALL_TESTS_PASSED`。kernel binary SHA-256 为 `55ed966770b14d843abb21bf203ee02bc04297efb24f2b3323ce58b3ad074e33`；源码 HEAD 仍是 `b73e5814087c9d33c5f0a35b66cc56be689d3dee`，dirty 文件数 53。完整命令、console、环境、内核 hash 和远端 SHA-256 清单见 [SCM short-read unit r1](../evidence/2026-11-19_t490-scm-shortread-unit-r1/)。

三轮探索失败也保留在仓库：第一轮 `UNITTEST=y` 编译被旧 procfs 单测签名阻断；修正该测试签名后，全 `knet` 运行暴露 stream tracing 在 kernel task 上 panic；加上 guard 后，全 `knet` 又遇到无关 netlink 既有测试预期不符。分别见 [unit r1](../evidence/2026-11-19_t490-compat-scm-unit-r1/)、[unit r2](../evidence/2026-11-19_t490-compat-scm-unit-r2/) 和 [unit r3](../evidence/2026-11-19_t490-compat-scm-unit-r3/)。单元过滤器支持模块路径，因此最终只运行 `knet::unix::stream`，将范围限定在 SCM_RIGHTS 涉及的代码路径。

两份候选 patch 已在相同隔离源码树中通过 reverse/apply 检查；补丁前后 `stream.rs` 和 procfs 文件 SHA-256 与单测产物记录一致。T490 上原始 `/home/mo/x-kernel` 的 53 个 dirty 文件未修改。
