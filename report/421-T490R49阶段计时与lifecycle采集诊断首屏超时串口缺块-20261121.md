# T490 R49 procfs 阶段计时与 lifecycle/memory 诊断（2026-11-21）

## 运行条件与状态

R49 使用冻结快照重建的独立候选 worktree `r49-procfs-timing-candidate`，叠加 stat22、resident-page/mapcount、tree rollup、dense PFN、direct-PTE 和 procfs phase-timing 六个补丁。rootfs 仍是正式 `/home/mo/x-kernel/images/pkg-installed.img`，SHA-256 `bab5c9f5…f7a9fdb1`；候选 kernel.bin SHA-256 `8e0a68a0…8d298d679`。T490 平台为 AArch64、2 GiB、4 vCPU、Cortex-A76、QEMU 10.2.1 pure TCG，platform check 15/15。

runner 参数已 dry-run 验证：diagnostic-only、1800秒首屏 deadline、900秒 1 Hz memory sampler、lifecycle preload、guest clock sync、30秒 process scan、25秒 family watchdog、一次真实 reload、420秒 diagnostic hold；dry-run 明确 `qemu_started=0`。真实轮在初始页等待约1800秒后超时，driver返回1；QEMU会话正常收尾，normalizer 1174/1174 PASS（无修复项），正式 gate RC78 是 diagnostic-only 跳过标志。QMP 共53张1280×800截图，53张 strict FAIL、any strict pass为0；末帧 `shot-53-at1811s` 失败。QEMU末段 watchdog仍报告 Weston/Chrome存活；没有记录到进程退出。

## memory export 无效

串口出现 `MP_PERF_MEMORY_EXPORT_BEGIN` 和 `MP_PERF_MEMORY_EXPORT_END`，两者都声明264块、压缩后50636字节。原始 console SHA-256 为 `69eb81ff…ff7b704`；严格解包实际识别248块，序号32–47整段缺失。提取器返回 `memory chunk sequence mismatch: expected 32, got 48`，完整 gap 见 [chunk-sequence-audit](../evidence/2026-11-21_t490-r49-candidate-lifecycle-memory/memory-export/chunk-sequence-audit.txt)。因此不接受任何memory CSV、RSS/PSS/USS峰值或阶段计时，不运行正式指标采集器。

同一console还出现 `MP_LEDGER_LIMIT=阻塞读：跨进程读 Chromium 子进程 procfs 会挂住读方；账本在其后停住（待内核侧修复）`。这轮的 liveness normalizer仍通过，但生命周期 probe 与内存样本位于缺块bundle内，无法完整核验 `browser_main_loop_ready`、`renderer_ready`、`first_valid_frame`。

## 解释边界和后续

这是一轮高观测负载诊断，不是性能样本或正式稳定性通过。缺块可能与串口/诊断日志争用有关，但单轮不能证明根因；console约48 MB，且包含大量Chromium futex/socket syscall输出。后续应单独降低 kernel/serial 诊断噪声并调整 bundle export pacing，在原始序号连续、SHA/gzip/tar复核通过前维持拒收。还需单变量比较sampler/preload负载与默认启动路径；当前白屏结果不能归因到单个探针。
