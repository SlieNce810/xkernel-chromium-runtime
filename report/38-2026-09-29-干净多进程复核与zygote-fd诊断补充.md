## zygote 阻塞定位

官方 Chromium zygote 实现将 `SOCK_SEQPACKET` 控制通道安装到 fd 3，并使用 `ppoll(fd=3)`、`recvmsg(fd=3)` 接收浏览器命令。现有远端窄范围证据显示：

- 浏览器确实创建了 `AF_UNIX`、`SOCK_SEQPACKET|SOCK_CLOEXEC` socketpair，并向 fd 3 发送过控制消息；
- zygote 进程已经启动并进入 `ppoll` 循环；
- 早期 fdmap 轮观察到 zygote 侧的接收 fd 出现过 4、11，而不是预期的 3；同一轮还出现过 `dup3(old_fd=10,new_fd=3)`；
- SCM_RIGHTS 的解析、发送和接收次数大体正常，说明问题集中在固定 fd 映射、socketpair transport 语义或 ppoll/readiness 链路，不能继续用“zygote 根本没启动”解释。

下一次远端主机恢复后，先做一个短诊断轮：只在 `sys_ppoll` 记录 `tid、进程名、nfds、pfd.fd、events、revents、返回值`，并与 `sys_dup3` 的 `old_fd/new_fd` 对齐。确认 zygote 是“轮询 fd 3 无事件”“fd 3 指向错误对象”还是“实际使用 fd 4/11”，再选择单变量修复。

## 按顺序的后续计划

### 内核修改

1. **固定 fd 与 exec 生命周期**：验证 `socketpair(SOCK_SEQPACKET|SOCK_CLOEXEC)`、`dup3(old,3,0)`、`execve` close-on-exec 和 fork 私有 fd 表是否保持同一个 `VfsFile` 对象；增加最小 guest probe，检查 exec 前后 fd 3 的类型、读写和 cloexec 位。

## 2026-09-30：zygote 首个崩溃点与后续多进程 A/B

通过在 `ReturnReason::Exception` 记录 AArch64 trap 上下文，并把运行时地址换算为 Chromium PIE 文件偏移，首次崩溃被定位为：zygote 执行 `fstatat(proc_fd, "self/task/", ...)` 后检查 `st_nlink >= 3`，而 x-kernel 的通用虚拟目录默认返回 `nlink=2`，触发 Chromium 的 `CHECK`，随后进入 `brk #0`，进程以 133 结束。二进制中的 fault offset 为 `0x883b084`，对应 `self/task/` 字符串附近的 `brk #0`。Chromium 上游 Linux sandbox 代码也明确执行同一检查。

内核已将 procfs 任务目录的链接数改为 `2 + thread_count`，并让 kvfs 创建目录 inode 时保留该值。修复后的 `mpprocfix` 轮不再出现 zygote `SIGTRAP/MP_EXCEPTION`，两个 zygote 可以保持存活；这项修复已经保留在远端源码中。
