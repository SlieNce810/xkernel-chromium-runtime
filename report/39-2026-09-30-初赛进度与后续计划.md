### 1. 内核修改方向：先证明 renderer 能完成首帧

1. **建立受控的 renderer 追踪点**。在临时分支中给 `clone/clone3`、zygote fd 请求、`execve`、`exit_group`、`set_tid_address`、`tgkill` 和 `prctl` 加进程号/线程名/返回值追踪；追踪只在诊断 Kconfig 打开，正式镜像关闭。目标是区分“renderer 没创建”“renderer 创建后立即退出”“renderer 已连接但 Viz 不提交”三种情况。
2. **补齐 Unix stream/SEQPACKET 的消息边界验证**。为跨进程 Mojo 常用的 `SOCK_SEQPACKET` 和 stream 分别增加多次 `sendmsg/recvmsg`、部分读取、`SCM_RIGHTS` 多 fd、`MSG_CMSG_CLOEXEC`、半关闭和 poll/epoll 测试；现有 sandbox probe 只覆盖 DGRAM/SEQPACKET 的最小路径，不能代替 Mojo 长消息和部分读取场景。
3. **审计共享内存和句柄生命周期**。重点检查 `memfd_create`、`F_ADD_SEALS/F_GET_SEALS`、`ftruncate`、`mmap(MAP_SHARED)`、`mprotect`、`mremap`、`close-on-exec` 和 fd 在 zygote/renderer/Viz 间传递后的引用计数。Chromium 的 renderer 位图和 Wayland buffer 可能走这一条路径。
4. **补齐事件等待语义**。核对 `eventfd`、`timerfd`、`epoll`、`ppoll_time64`、futex 普通/PI/robust-list、`clock_gettime` 和 `rseq` 的返回值与唤醒顺序，特别是“写入后先发布控制消息，再发布数据”的并发顺序。
5. **继续 DRM/Wayland ABI 对照**。保留 simple-shm 作为 compositor 基线；对 Chromium 需要的 render node、DMA-BUF、`wl_shm` 和 Wayland fd 传递分别做最小客户程序，不把 GPU/Vulkan 失败误归因到 DRM property ioctl。
6. **procfs 继续从最小占位值改为可用值**。已完成 uptime；下一步补充 CPU jiffies、进程状态/线程状态、`/proc/<pid>/fdinfo` 中 Chromium 会读取的字段，并让测量脚本使用线程名和 clone/exit 事件，而不是只依赖缓存的 `/proc/<pid>/cmdline`。

### 2. 启动优化方向：形成可复现的启动矩阵

每次只改变一组参数，固定基础镜像、eudev overlay、页面、内核 hash 和 guest 观察窗：

1. **软件基线**：`--disable-gpu --disable-gpu-compositing --disable-threaded-compositing`，同时保留 zygote/多进程；确认 GPU 进程是否还启动以及 Viz 是否能提交。
2. **ANGLE GLES 对照**：`--use-gl=angle --use-angle=gles`；若仍失败，记录确切 EGL/GL loader 错误，不再把 `legacy` 当作 SwiftShader 选项，因为当前 Chromium 已经移除旧实现。
3. **ANGLE SwiftShader/Vulkan 对照**：只用于记录扩展缺失，不作为正式验收参数；正式启动不能依赖 `VK_EXT_headless_surface` 等当前镜像未提供的扩展。
4. **GPU 进程形态**：比较 separate 与 `--in-process-gpu`，但必须把 GPU 初始化结果和 renderer/Viz 首帧分别记录；“浏览器不退出”不等于页面已绘制。
5. **页面加载节奏**：首帧通过后再加入 index/interaction/layout 三页、10 次冷/热加载、键鼠事件和页面间导航；每次保存 PPM、HTML/JS 断言、renderer 创建时间和退出码。

### 3. 多线程兼容方向：以 Chromium/Weston 实际线程模型为准

1. 核对 `clone` flags、线程组 TGID/TID、`/proc/<pid>/task`、`gettid`、`tgkill`、`set_tid_address` 和 clear-tid。
2. 核对 pthread 使用的 futex wait/wake、PI、robust-list、优先级继承和超时钟域；保证被杀线程、父进程退出和 socket half-close 时不会留下永久等待。
3. 核对 `rt_sigaction`、`rt_sigprocmask`、`rt_sigaltstack`、`signalfd`、`eventfd`、`timerfd`，并验证 zygote fork 后信号屏蔽集和 PDEATHSIG。
4. 核对 `sched_getaffinity`/`sched_setaffinity`、CPU 数量和 `rseq`；Chromium 的线程池和分配器会根据这些结果选择实现。
5. 使用线程名、线程创建/退出事件和 procfs task 快照统计“实际 renderer/Compositor/IO 线程数”；暂不使用当前缓存式 cmdline 的 `RENDERER_COUNT` 作为唯一判据。

## 性能分析启动条件和方法

当前不能把 `strace`、`perf`、eBPF 或火焰图结果称为初赛性能结果，因为功能门槛还没有通过。当前 guest 的 `ptrace` 也会返回 `Function not implemented (38)`，因此现有 strace 只能作为“工具缺口”记录。

以上结论针对此前的默认多进程范围。2026-10-02 起，单进程范围已经通过功能门禁，并完成五次单进程初赛测量；正式 `perf/eBPF` 采样仍受 T490 权限限制，详见 [41-初赛单进程性能报告](41-初赛单进程性能报告.md)。

功能门槛通过后按以下顺序采样：

1. **strace**：短启动轮使用 `strace -ff -ttt -T -yy -s 256`，统计 `clone/execve/futex/epoll_wait/ppoll/sendmsg/recvmsg/mmap` 的次数、错误率和尾延迟；先补齐 guest `ptrace`，否则改用内核 syscall trace。
2. **perf**：用 `perf stat` 记录 cycles、instructions、context-switches、page-faults、cpu-migrations；用 `perf record -g` 分别采样 browser、renderer、GPU/Viz 和 Weston。
3. **eBPF**：功能支持后用 tracepoint/bpftrace 采集 `sched_switch`、`sys_enter/exit`、futex、block I/O、TCP connect/keepalive 和 page fault；若 guest 没有 BPF，使用 Linux host/QEMU 侧等价 trace，并在报告中明确观测边界。
4. **火焰图**：`perf script` 生成 folded stacks，再用 Brendan Gregg FlameGraph 输出 browser、renderer、Weston 三张图；同时保留原始 `perf.data`、脚本、内核 hash 和采样窗口。
5. **对比实验**：固定同一页面和 10 次加载，比较 baseline、内核修复、启动参数修复三组；只在稳定性和像素断言都通过后比较吞吐、首帧延迟、CPU/RSS 和上下文切换。
