## 失败定位

稳定性门禁以 `page_ready` 和 `monitor_end` 事件的 `t_ns` 差作为计时依据。driver 内部计时和两事件写入时间点有约 15 ms 的边界差异，所以即使 driver 报告 1800 秒，正式门禁仍正确拒绝不足 1800 秒的事件窗口。下一轮将把 hold 设为 1805 秒，保留明确余量，不改变门禁阈值。

原始 driver 会把 `MP_FAMILY_COUNT=...` 误当作 `MP_FAMILY` 结构快照，导致最近一次有效家族被空快照覆盖。离线事件规范化可在 35 秒新鲜度内修复 57 个空记录；但序号 185 和 348 没有新鲜且包含完整进程家族的快照。相关原始快照在序号 177/189 和 342/353 之间显示完整角色集合有间断。规范化器没有填造 PID 或复用过期记录，保留这两个失败。

Watchdog 在对应时刻仍报告 Weston=yes、chrome=yes；这只能证明 compositor 和 Browser 存活，不能替代缺失的进程家族证据。`zygote_child` 是依据父子进程拓扑观察得到的角色标签，不等同于 Chromium 内部 RendererReady 事件。

## r4 复验修正

- stability driver 只解析带 `MP_FAMILY label=` 的完整快照，忽略 `MP_FAMILY_COUNT`。
- observer 每 10 秒尝试输出一次家族快照，并核对记录 PID 的 starttime 和 PPID，避免 PID 复用造成的假存活。
- 规范化器仅从 35 秒内的新鲜完整快照修复空 liveness 记录；没有合格快照时保持失败。
- 正式保持窗口调为 1805 秒，门禁仍按事件同钟时间检查至少 1800 秒。
- r3 结束后验证的 14 项 Python 单元测试全部通过；两个 shell 脚本 `bash -n` 和相关 Python `py_compile` 通过。

下一轮在 T490 启动前须上传以上脚本并核验 SHA-256 与仓库一致，再以新 run tag 运行；若仍有真实家族快照空窗，继续记失败并分析进程来源。
