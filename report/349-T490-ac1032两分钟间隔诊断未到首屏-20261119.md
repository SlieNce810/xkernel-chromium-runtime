# T490 `ac1032` 两分钟间隔诊断未到首屏（2026-11-19）

## 结论

在最终候选 kernel `ac1032fe98c382cc37646a12453b7141b789c9abfe1651ff5f8f1e0263767fa2`、相同 rootfs 和 2 GiB AArch64 纯 TCG 条件下，将诊断重载间隔设为 120 秒后，本轮始终没有通过首页 strict 判据。QEMU 运行 1,804.2 秒并正常结束；首屏 driver 完成 59 次失败轮询，期间没有发出任何重载请求。

QMP 成功保存 53 张 `1280x800` 原始截图。逐张严格检查均有 6 项核心条件失败；`shot-15-at0663s.ppm` 到 `shot-53-final.ppm` 画面为纯白，首尾帧差异为 0 像素。末次看门狗记录到 Weston、Chrome 仍存活，guest 可用内存约 570 MiB；串口日志未检出 OOM。由于页面从未 ready，本轮不构成 nav-08 超时的复现，也不构成稳定性通过或性能样本。

远端结果为 `STABILITY_DRIVER_RC=1`、`STABILITY_ROUND_RC=0`、事件归一化 `RC=0`；诊断模式按设计跳过正式 gate（`RC=78`）。driver 的末事件是 QEMU 关闭 QMP 后的 `Broken pipe`：当时 readiness timeout 配置为 2,400 秒，而 QEMU 会话上限为 1,800 秒。

## 对照与判断边界

同一候选在 30 秒间隔诊断中曾通过 8/8 次重载（[report 348](348-T490-ac1032短间隔重载不复现nav08超时-20261119.md)）。另一轮正式候选稳定性试跑则通过首屏、完成 1,805 秒保持，但第八次重载后出现 Chromium “Page Unresponsive”（[report 345](345-T490-ac1032稳定性轮第八次重载页面无响应-20261119.md)）。本轮从启动阶段就没有渲染出页面，故不能将这三种结果解释为重载间隔导致的性能或稳定性变化；候选启动/绘制仍存在未解释的间歇性失败。

当前统一审计为 `INCOMPLETE`：历史 2 GiB 基线 R10 gate 仍为 PASS，最终候选正式稳定性为 FAIL；2 GiB 浏览器评分 16/20，兼容性摘要 PASS，性能 before/after 有效轮数仍为 0/0。诊断模式结果被 audit 排除，未改变上述正式状态。审计快照见 [goal-audit r4](../evidence/2026-11-19_t490-final-report-r4/goal-audit.json)。

## 采集器修正

本轮暴露出诊断等待时限长于会话时限的问题。仓库中的 `scripts/t490/run_stability_round_mp.sh` 现会在默认首屏 timeout 将超出 session duration 时，将其限制为 `session duration - 200` 秒；显式配置的超长 timeout 会在启动前拒绝。新增的 `--dry-run` 显示解析后的配置而不启动 QEMU。

本地验证结果：`bash -n` 和 `--help` 通过；1800 秒诊断会话的默认首屏 timeout 解析为 1600 秒；正式 4200 秒配置仍为 2400 秒；显式设置 2400 秒配 1800 秒会话被拒绝，且未启动 QEMU。这项 runner 修正让后续短会话能先得到明确的首屏 timeout 和截图，而不是等会话上限关闭 QMP。它没有修复本轮观察到的白屏。
