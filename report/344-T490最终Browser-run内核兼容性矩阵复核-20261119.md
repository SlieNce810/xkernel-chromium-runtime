# T490 最终 Browser-run 内核兼容性矩阵复核（2026-11-19）

## 结论

在 Chromium 最终 HTML/process run 使用的同一 AArch64 kernel binary SHA `ac1032fe98c382cc37646a12453b7141b789c9abfe1651ff5f8f1e0263767fa2` 上重跑 focused compatibility bundle。2 GiB pure-TCG guest 实际运行 303.3 秒；platform gate 15/15，bundle 返回码 0。

- 全量 `compatprobe` ABI 矩阵：38/38。
- SCM_RIGHTS short-read：6/6，fd 在首个 1-byte read 到达，payload 完整。
- memfd sealing：12/12，包括 `MFD_ALLOW_SEALING` 单独启用、F_SEAL_WRITE/GROW/SHRINK、sealed pwrite/mmap 拒绝、all-ones flags `EINVAL`、`MFD_NOEXEC_SEAL` 设置 `F_SEAL_EXEC`。
- procfs memory probe：RSS/PSS/USS 在匿名、file-private/shared、fork/COW 和 unmap 阶段均为有效数值。
- `MADV_DONTNEED` 范围含 hole 时返回 Linux 预期 `ENOMEM`；native T490 Linux 7.0 与 WSL2 Linux 5.15 对照也返回 `ENOMEM`。

## MADV_DONTNEED 差异和修复

同一 C probe 在 native Linux 7.0 与 WSL2 Linux 5.15 对 `[mapped page, unmapped page, mapped page]` 的 3-page `MADV_DONTNEED` 调用都返回 `-1/ENOMEM`。x-kernel 旧候选错误地忽略 VMA gap 并返回成功；此处 C probe 的旧 PASS 预期也错误。

最终候选在 `mm/memspace/src/aspace.rs::MmSpace::madvise_dontneed` 先验证请求区间由连续 VMAs 覆盖；发现 gap 时返回 `KError::NoMemory`，且不丢弃覆盖区间中的有效页。修复补丁见 [madvise-hole-ENOMEM.patch](../patches/compat/madvise-hole-ENOMEM.patch)，单元回归 `madvise_dontneed_rejects_unmapped_gaps` 随 `memspace::aspace` 的 14 项测试全部通过。

## memfd sealing 差异和修复

候选的 `MemfdFlags::allows_sealing` 原来用 `contains(MFD_ALLOW_SEALING | MFD_NOEXEC_SEAL)`，要求两个 bit 同时设置。Linux 允许仅用 `MFD_ALLOW_SEALING`，但原候选创建出的 memfd 不能添加 seals。最终实现把两个条件改为逻辑 OR；补丁见 [memfd-sealing-flags.patch](../patches/compat/memfd-sealing-flags.patch)。修复后 guest 和 native Linux memfd probe 均 12/12。

最终 Browser run 的 7 次 `memfd_create` 失败参数经独立诊断为 `0xffffffff`；native Linux 同样返回 `EINVAL`。它们是无效 flags 检查，不是 `MFD_NOEXEC_SEAL` 的运行失败；有效 `MFD_ALLOW_SEALING` 和 `MFD_NOEXEC_SEAL` 均由本轮 probe 直接覆盖。
