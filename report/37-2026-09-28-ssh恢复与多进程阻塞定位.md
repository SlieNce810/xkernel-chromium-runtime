# 37 · SSH 恢复后的初赛门禁复核与多进程阻塞定位

日期：2026-09-28

## 当前结论

SSH 公钥问题已经解决并完成实机验证。使用 T490 专用密钥连接 `10.249.63.140:22`，远端主机返回 `T490_KEY_OK`，可以继续执行编译、镜像注入和 QEMU 会话。远端源码仍是 dirty working tree，基线 HEAD 为 `c2eabd5`；后续证据必须同时记录源码状态、kernel image SHA-256、基础镜像 SHA-256 和页面 SHA-256。

初赛验收目前还不能判定通过。官方三页的单进程渲染、Weston/Wayland、DRM/sysfs、输入设备和基础像素判据已经有通过证据；默认多进程 Chromium 的 renderer gate 仍为 0，因此不能进入正式性能统计，也不能声称已经满足初赛完整验收。

## 已确认的事实

1. T490 使用 AArch64 QEMU 纯 TCG，QEMU 10.2.1、2 GiB 内存、4 vCPU。有效 overlay 含 eudev、seatd、libinput、SwiftShader 和 strace。
2. x-kernel 已发现并发布两只 virtio 输入设备：`QEMU Virtio Keyboard` 和 `QEMU Virtio Mouse`。`/dev/input/event0`、`event1`、`/sys/class/input/input0`、`input1` 均存在；Weston 能在包含 eudev overlay 的轮次建立 `wayland-1`。
3. 默认多进程命令不含 `--single-process` 和 `--no-zygote`。浏览器本体和 `NetworkService` utility 可以启动，`FileURLLoader::Start` 能加载官方入口页，但 renderer 数量持续为 0。
4. 延长观察窗后，Chromium zygote 日志出现 `ZygoteMain: initializing 0 fork delegates`。这表明阻塞点位于 zygote 启动之后、renderer 子进程出现之前；单纯改变 GL 模式、禁用 NetworkService、SVE/SME/MDWE `prctl` 探针和临时 `PDEATHSIG` no-op 均没有使 renderer gate 通过。
5. 受控 clone/exec/Unix socket 追踪显示：clone、execve、SCM_RIGHTS 发送和接收大多返回成功；因此“所有子进程都无法创建”的早期判断已经排除。guest 内 strace 仍受到 ptrace 未实现/异常 wait status 限制，不能作为主要根因证据，后续应使用内核窄范围 trace、host 侧进程快照和 ktrace。
6. 已发现但暂未纳入正式结论的 ABI 修复方向：`MSG_CMSG_CLOEXEC` 在原实现中没有把 SCM_RIGHTS 接收 fd 标记为 close-on-exec；该补丁已在远端完成编译验证，但单轮对照尚未让 renderer gate 通过。CMSG 对齐实验因改变了 eudev 输入节点权限而导致 Weston 预检失败，已经回退，不能直接作为有效性能结果。

7. 诊断脚本本身也完成了一次门禁修正：在 AArch64 TCG 下逐进程读取 `/proc/*/maps`、`wchan` 和 `status` 会让采样循环在约 25 秒后停止。当前远端诊断入口已改为 ps-only 进程快照和 ps-only RSS 汇总，独立的 maps 深度探针不再阻塞 renderer gate 采样。修正后的轮次已经稳定记录到两个 `--type=zygote` 进程，但 renderer 仍为 0。

最终远端 clean build 已通过，kernel image SHA-256 为 `88160e63a6e22605351b523a7b618832a850b70852ea4cf5f828e4b1e6969555`；当前没有残留 QEMU、run-session 或 round 进程。该 fingerprint 对应的有效 overlay 轮仍记录 `MP_WESTON_SOCKET=wayland-1`、`MP_RENDERER_SEEN=0`、`MP_GATE=0`。

## 后续按顺序执行

### 1. 先完成多进程根因闭环

- 保持有效 guest overlay、`MP_TRACE=0`，单变量运行，避免把 eudev/Wayland 预检失败误判为 renderer 失败。
- 在 kernel `clone`、`execve`、`sendmsg`、`recvmsg`、`wait4`、信号退出路径增加可开关的窄范围记录，至少记录 tid、flags、返回值、exit code、信号和目标 fd；默认关闭，诊断轮才打开。
- 记录 zygote 子进程的实际 argv、首次 `ZygoteMain`、首次 renderer clone、renderer exec、SIGCHLD/wait 状态。重点确认 zygote 使用的是 socketpair `SOCK_SEQPACKET` 还是 stream，以及 command fd 是否收到完整消息。
- 核对 `SCM_RIGHTS` 的接收 fd 是否带 `FD_CLOEXEC`，控制消息长度和数据区是否符合 Linux `CMSG_ALIGN`。CMSG 对齐修改必须先补 netlink/eudev 回归，再进入 Chromium A/B；否则会把权限变化误判为 renderer 退化。
- 单变量顺序建议为：`MSG_CMSG_CLOEXEC` → zygote `SOCK_SEQPACKET` 保序语义 → `waitid`/SIGCHLD → exec 后线程/地址空间状态 → renderer clone 的 page-table 和 TLS。每项都用同一镜像、同一页面、同一 observation window。

### 2. 内核修改方向

- 进程创建：验证 `clone`/`clone3` 的 exit signal、TLS、parent/child tid、`CLONE_VM` 组合与 Chromium AArch64 ABI；对 fork child 的 page-table root、register context、clear-child-tid 做日志和单测。
- IPC：完整实现 `SOCK_SEQPACKET` 的消息边界；验证 ancillary queue 与数据包一一对应，避免 stream ring 把多个 zygote command 合并或拆分。
- fd 生命周期：实现并测试 `MSG_CMSG_CLOEXEC`、`F_DUPFD_CLOEXEC`、exec 时 close-on-exec 清理和 SCM_RIGHTS 接收后的引用计数。
- 等待与信号：补齐 `waitid` 最小 Linux ABI，至少支持 `P_PID`、`P_ALL`、`WEXITED`、`WNOHANG`、`WNOWAIT`，并从现有 child exit status 生成 `siginfo_t`；同时记录 zygote/renderer 的退出码和 SIGCHLD。
- procfs/启动性能：优化 `/proc/self/maps` 与 `/proc/self/status` 的读取粒度和重复解析开销，避免 TCG 下 zygote 启动被数百次小读拖到 observation window 之外。

### 3. 启动优化方向

- 固化一套启动 profile：Wayland + pixman + SwiftShader + in-process GPU 作为功能基线；NetworkService、GL、sandbox 选项通过白名单变量注入并记录完整 argv。
- eudev/seatd/libinput overlay 必须作为证据输入记录 SHA-256；预检失败时保留 Weston、seatd、udevd、input 节点和 uevent 日志。
- 诊断轮与性能轮分离：诊断轮允许 kernel trace/strace；性能轮 `MP_TRACE=0`，避免 trace 输出和日志 I/O 污染样本。
- renderer gate 通过后先跑一轮短稳态和三页功能，再跑 600 秒稳定性；任何一项失败都保留独立 evidence 目录，不覆盖旧轮。

### 4. 多线程兼容方向

- 先确保 `CLONE_THREAD | CLONE_VM | CLONE_SIGHAND | CLONE_FILES` 的线程创建、TLS、robust-list、futex、clear-child-tid 一致，重点观察 zygote 内线程和 NetworkService 线程。
- 逐项验证 `membarrier`、`rseq`、`set_robust_list`、`prctl(PR_SET_NAME/PR_SET_DUMPABLE/PR_SET_NO_NEW_PRIVS)` 的返回值和继承语义；兼容 no-op 必须记录实际安全边界，不能用成功掩盖未实现状态。
- exec 仅允许单线程进程，若 renderer/utility 在 exec 前后存在多线程，必须记录 `process_task_count` 和对应退出原因，避免错误返回 `EWOULDBLOCK` 后静默丢子进程。
- 用 futex PI、pthread clone、Chrome zygote 三组最小复现验证调度、优先级和跨 CPU 唤醒，再进入浏览器长稳态。

### 5. 功能通过后的性能分析

只有当默认多进程 `MP_GATE=1`、三页官方判据、点击/键盘交互和 600 秒稳定性全部通过后，才执行正式性能分析：

- `strace -ff -ttt -T -yy`：采集启动和一轮页面交互，统计 clone/execve/futex/epoll/poll/sendmsg/recvmsg/mmap 的次数、错误和耗时；不把 strace 轮混入性能 CSV。
- `perf stat`/`perf record`：在 Linux T490 host 侧采集 QEMU 进程 cycles、instructions、context-switches、page-faults 和 CPU 时间，guest 内 `perf_event_open` 仍需单独标记是否为 dummy。
- eBPF/bpftrace：跟踪 QEMU vCPU 线程调度、syscall 延迟、block I/O、网络包和上下文切换；先运行 verifier/权限自检并记录 kernel、BTF、脚本 SHA-256。
- 火焰图：用 `perf script` 生成 folded stacks，再用 FlameGraph 生成 SVG；分别保留 Chromium browser、QEMU vCPU、x-kernel host helper 三类图，报告采样频率、采样时长和丢样本数量。
- 每项结果写入独立 `evidence/YYYY-MM-DD_t490-<scenario>/`，保留 `cmd.txt`、`env.txt`、`manifest.txt`、`timestamps.csv`、原始 trace 和生成的 SVG/CSV。

## 当前最小验收门槛

下一轮不以“浏览器进程存在”作为通过条件，必须同时看到：

```text
MP_WESTON_SOCKET=wayland-1
MP_RENDERER_SEEN=1
MP_RENDERER_MAX_STREAK>=12
MP_GATE=1
```

并在同一证据目录中找到官方页面、输入交互和稳定性结果。完成这些门槛前，初赛阶段应标记为“环境和单进程路径基本完成，多进程 renderer 与正式性能分析未完成”。
