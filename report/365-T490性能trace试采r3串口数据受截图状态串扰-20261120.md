# T490 Chromium startup trace 试采 R3：串口数据受截图状态串扰（2026-11-20）

## 结论

R3 确认 trace 参数生效，并证明 Chromium 在运行期生成了 3,920,137 字节的 startup trace。串口 exporter 成功输出 BEGIN、DATA 与 END 标记，但数据流与周期截图状态文字共用控制台输出后，有一个 DATA 行被打断；重组 gzip 在第 10,808 个零基数据块处失败。trace 未能通过 SHA-256 和 JSON 校验，本轮不能作为性能样本。

R3 的页面诊断结果为首页严格通过、1/1 QMP 重载通过、保持 550 秒。29 张周期截图中 11 张未通过严格像素判据（10 张属于 warm-up，1 张发生在首个通过帧后），末帧通过；因此仍不满足连续稳定性验收。事件归一化也返回失败，原因是完整进程族快照陈旧 37.041 秒，超过 35 秒上限。两项失败都随完整诊断证据保留。

## 证据与分析

控制台头记录：

- `run_id=codex-2026-11-20-perf-trace-r3`
- 原始长度：3,920,137 字节
- 原始 SHA-256：`3a342f89aa4a51095ecea45d04a23fd283fe4c8dce3d0f7b05a9de0e802b6990`
- 串口 DATA 标记：12,259 行；可解析完整数据块：12,258 行
- gzip 解压失败：`invalid stored block lengths`，零基数据块 10,807

日志第 170,709 行中，`MP_PERF_TRACE_DATA run_id=co` 后插入了 `[2026-11-20 08:28:03] screendump OK` 文本。这与 QEMU 会话每 30 秒输出周期截图状态时段重合，解释了单条串口块被破坏。停机后的 `debugfs` 检查也未在 QEMU 使用的 `KERNEL_DIR/disk.img` 中找到 `/root/mp-perf-trace.json`；因此 R3 只能依靠串口转发。

稳定性归档仍是 diagnostic-only：driver pass=1、重载1/1、hold=550秒、周期PPM29/29；但严格像素摘要为 `strict_fail=11`、`post_pass_fail=1`、`last_frame_strict_pass=1`。归一化372个事件时无解析错误，但一条完整进程族快照年龄37.041秒，超过35秒阈值。

完整证据包位于 [R3 evidence](../evidence/2026-11-20_t490-candidate-perf-trace-r3/)，非PPM归档 SHA-256 为 `bf9deefcbed57de2d979eaa5560b1a4a6014bc91c2597fd44cf7d100f28251e5`。31 张原始 PPM 保留于 T490；仓库保存对应 SHA 清单及三张 PNG 预览。

## 后续动作

R4 将把周期截图间隔设为 1,200 秒（会话预计在约 1,110 秒结束），避免周期截图状态文字落入约 500 秒的串口导出窗口；数据块加入连续序号和 END 块数，抽取器在压缩、长度、SHA 或 JSON 校验失败时返回明确错误。R4 仍为诊断试采，只有 trace 完整可复核后才继续建立事件映射和四项指标采集。
