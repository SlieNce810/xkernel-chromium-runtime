机器门禁：

```bash
python3 scripts/verify_pixel_policy.py <evidence>/screenshots
```

远端证据目录：`/home/mo/xk6/evidence/2026-11-02_t490-final-mp-20261102c`

- QEMU 命令行包含固定画幅参数：`-global virtio-gpu-pci.xres=1280 -global virtio-gpu-pci.yres=800`；
- 实际 3 张 PPM 全部为 640×480、921,615 字节；
- `verify_pixel_policy.py` 全部 FAIL；
- guest Weston 日志报告 `could not open DRM device 'card0'`、`no drm device found`、`failed to create compositor backend`；
- 本轮不得计入图形稳定性、多进程 renderer 或性能 PASS。

后续 `final-mp-20261102d/e` 轮移除了脚本里伪造的 `faux` DRM sysfs，总线改为读取真实 `/dev/dri/card0` 和 `/sys/class/drm`。结果仍为 `MP_GATE=0`、`WAYLAND_SOCKET_MISSING=1`；因此当前阻塞已经从脚本伪造拓扑收敛到真实 DRM sysfs/udev 与 Weston 设备枚举链路。

## 当前阻塞与下一步

640×480 不是 QEMU 参数未写入，而是 guest 没有可打开的 DRM `card0`，导致 Weston 无法建立真实 compositor 输出，QEMU 只保留占位 framebuffer。下一步必须完成以下链路并重新取证：

1. 检查当前 rootfs/overlay 是否包含与 kernel commit 匹配的 `/dev/dri/card0`、virtio-gpu sysfs 和 DRM 节点；
2. 在 guest 内记录 `/dev/dri`、`/sys/class/drm`、`modetest`/DRM probe 和 Weston 启动日志；
3. 只有 Weston 成功打开 DRM、screendump 稳定为 1280×800 后，才继续多进程 renderer 和 30 分钟稳定性轮；
4. 所有失败轮保留原目录，但从最终索引中标记为 `NON_PASS_PIXEL_POLICY`。
