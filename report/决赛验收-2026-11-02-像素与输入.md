# 决赛验收记录：固定画幅与真实输入（2026-11-02）

## 口径

决赛所有功能和性能截图固定使用 1280×800，PPM 文件必须是 P6、1280×800、3,072,016 字节。640×480 属于启动占位画面，不能作为 PASS，也不能通过“众数尺寸”降级放行。

机器门禁：

```bash
python3 scripts/verify_pixel_policy.py <evidence>/screenshots
```

这轮可以作为 QMP 事件注入链路的候选证据。它还不能单独证明 Chromium 已收到事件：当前镜像的 guest 持久日志存在 9 月旧内容，必须等 Weston/evdev 日志回收改成当前轮后，才能把它升级为真实应用输入 PASS。

## 多进程轮

远端证据目录：`/home/mo/xk6/evidence/2026-11-02_t490-final-mp-20261102c`

- QEMU 命令行包含固定画幅参数：`-global virtio-gpu-pci.xres=1280 -global virtio-gpu-pci.yres=800`；
- 实际 3 张 PPM 全部为 640×480、921,615 字节；
- `verify_pixel_policy.py` 全部 FAIL；
- guest Weston 日志报告 `could not open DRM device 'card0'`、`no drm device found`、`failed to create compositor backend`；
- 本轮不得计入图形稳定性、多进程 renderer 或性能 PASS。

后续 `final-mp-20261102d/e` 轮移除了脚本里伪造的 `faux` DRM sysfs，总线改为读取真实 `/dev/dri/card0` 和 `/sys/class/drm`。加入 DRM udev 冷插拔后，`final-mp-20261102f` 已经完成 DRM 打开和 Pixman 初始化，但因为没有 input seat，Weston 仍退出。给 renderer 诊断入口加入 `--continue-without-input` 后，`final-mp-20261102g` 的 `MP_WESTON_SOCKET=wayland-1` 和 4 张 1280×800 截图全部通过；当前剩余门槛是 Chromium browser 存活但 `MP_RENDERER_COUNT=0`，尚未形成 zygote/renderer 进程。

这把图形链路和 renderer 进程链路分开了：`--continue-without-input` 只允许 renderer 诊断轮启动 compositor，不能作为真实键鼠通过证据；真实输入必须继续使用独立输入轮。

历史诊断对照显示，加入 `--no-zygote` 时 Chromium 能出现 3 个 renderer；保留默认 zygote 时只出现 browser 和 zygote，renderer 数为 0。这个对照证明当前剩余问题集中在 zygote 创建 renderer 的 clone/IPC 路径，不能用 no-zygote 结果替代决赛多进程验收。

## 当前阻塞与下一步

640×480 不是 QEMU 参数未写入，而是 guest 没有可打开的 DRM `card0`，导致 Weston 无法建立真实 compositor 输出，QEMU 只保留占位 framebuffer。下一步必须完成以下链路并重新取证：

1. 检查当前 rootfs/overlay 是否包含与 kernel commit 匹配的 `/dev/dri/card0`、virtio-gpu sysfs 和 DRM 节点；
2. 在 guest 内记录 `/dev/dri`、`/sys/class/drm`、`modetest`/DRM probe 和 Weston 启动日志；
3. 只有 Weston 成功打开 DRM、screendump 稳定为 1280×800 后，才继续多进程 renderer 和 30 分钟稳定性轮；
4. 所有失败轮保留原目录，但从最终索引中标记为 `NON_PASS_PIXEL_POLICY`。
