# Unix 数据包语义修复与多进程复核（2026-11-07）

## 1. 发现

对同一份 `unix_bulk_probe.c` 做 T490 guest 复现时，b73 基线出现三类与 Linux
不一致的行为：

```text
stream_4k       PASS
stream_64k      PASS
stream_1m       PASS
stream_nonblock PASS
seqpacket_8k    FAIL  sent=8192 recvd=4096 hash_match=0
small_stream    PASS
peek            HANG（90 s 超时）
```

根因分别是：

1. `SOCK_SEQPACKET` 消息在一个用户读请求中跨过 VM I/O 窗口时，
   `DgramTransport::recv` 只完成第一次写，4 KiB 后把数据包尾部丢弃；
2. Dgram/seqpacket transport 没有把对端 `SHUT_WR` 状态传播到接收端，
   队列清空后仍返回 `WouldBlock`，导致读端永久等待；
3. `StreamTransport::recv` 无条件推进 ring-buffer 读指针，
   `MSG_PEEK` 实际上消费了数据，后续真实读取没有数据可读。

## 2. 修复

远程 x-kernel worktree 当前保留两个文件的最小修复：

- `net/knet/src/unix/dgram.rs`
  - 为连接端点增加共享的 peer write-shutdown 标志；
  - 在接收端正确返回 EOF，并唤醒等待者；
  - 增加 packet tail 保存，跨页/部分用户缓冲时下一次 read 继续取尾部；
  - 增加 `MSG_PEEK` packet 保存，peek 不消费数据和 ancillary；
  - `recv` 循环写入可用用户缓冲窗口，避免 4 KiB 截断。
- `net/knet/src/unix/stream.rs`
  - `MSG_PEEK` 路径不推进 ring-buffer read index；
  - peek 不弹出 ancillary，不触发 writable 重新唤醒。

## 4. 对默认多进程浏览器的影响

修复后的默认多进程轮：
`/home/mo/xk6/evidence/2026-11-07_t490-mp-dgrampeek-b73-20261107-r1/`

renderer 仍可创建并运行，且可见多个 renderer 的线程数、RSS 和 CPU 增长；但
官方 index 页面仍未通过，首帧仍是白屏/WARMUP。由此得到两个边界：

- Unix 大消息、EOF 和 stream `MSG_PEEK` 确实是 x-kernel 的兼容性缺陷，已修复；
- 它们不是当前多进程 HTML 白屏的充分修复，剩余断点仍在 renderer 建连后的
  导航提交、Wayland configure/ack 或 Chromium 内部绘制/共享资源交付。

不能把这轮“renderer 进程数量增加”写成页面已恢复；`ppm_assert --strict` 仍必须
通过 official-index 才能关闭 P0。
