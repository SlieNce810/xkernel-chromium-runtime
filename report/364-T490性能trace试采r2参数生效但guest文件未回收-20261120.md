# T490 Chromium 启动 trace 试采 R2：参数生效，guest trace 文件未回收（2026-11-20）

## 结论

补上 `EXTRA_FLAGS` 注入后，R2 的 Chrome 实际 `CHROME_ARGS` 和 Browser `execve` argv 都包含 `--trace-startup`、类别列表、`--trace-startup-file=/root/mp-perf-trace.json` 和500秒时长。Chromium stdout 四次带出同一条时间戳日志 `Completed startup tracing to /root/mp-perf-trace.json`，证明 startup tracing 结束并报告了目标文件路径。

trace 文件仍未进入证据包：`round_assert.sh` 本轮按旧逻辑从 `$HOME/x-kernel/disk.img` 回收guest文件，而 QEMU commandline 实际写入 `/home/mo/xk6/worktrees/xk-compat-fix-r1/disk.img`。本轮结束后的 debugfs 检查对 worktree disk 同样没有找到 `/root/mp-perf-trace.json`，所以不能断言仅仅修正回收路径就能恢复文件。R3 工具修复同时做了两件事：`round_assert.sh` / `pull_guest_logs.sh` 跟随 `KERNEL_DIR` 读取正确镜像；guest autorun 在 Chrome 报告trace完成后，通过 gzip/base64 serial marker 导出文件内容，避免日志文件只在guest易失挂载中可见。

稳定性诊断：初始首页 strict 在558.910秒通过，nav-01真实QMP重载首次截图通过，保持550.001秒，1/1重载；29/29周期QMP截图成功，首个周期strict PASS 为shot-11-at0542s，post-pass失败0。事件归一化382/382通过；仅为diagnostic-only，gate RC78，不能作为正式稳定性或性能样本。trace数据未回收前，四项性能指标仍为0/0有效样本。
