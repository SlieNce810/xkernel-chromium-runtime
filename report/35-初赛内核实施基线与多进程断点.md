## 已核实的多进程断点

- `input-seat29-browser-diagnostics` 的 Chromium 普通模式连续报告 GPU 子进程启动失败（`error_code=1002`）并以 `GPU process isn't usable` 退出；同轮还报告找不到 DRM render-node。该证据说明 GPU 路径失败，尚未证明它是 renderer 缺失的唯一根因。
- `input-seat34-swiftshader-normal` 使用 `--in-process-gpu`，进程快照能看到两个 zygote 和 network utility，未看到 `--type=renderer`。Chromium 同时产生 DBus 缺失和 TCP_KEEPIDLE 不支持等日志；未观察到足以锁定 renderer 失败原因的 syscall/errno 轨迹。
- `input-seat36-singleprocess-pi-fixed` 使用 `--single-process --no-zygote` 后才取得首页画面。该轮证明单进程诊断路径，不证明默认多进程 renderer 已通过。

因此，多进程修复仍是待诊断事项。除非后续标准客户端或 syscall 轨迹确认 Linux 行为差异，不对 DRM、clone/wait、Unix FD 传递等模块作猜测性改动。

## 当前上游副本的内核缺口核对

在 `80b4836` 源码中确认：

- `core/ksyscall/src/task/rusage.rs` 仍将 `ru_maxrss`、`ru_minflt`、`ru_majflt` 固定写为 0；`Process` 的现有累计统计主要覆盖 CPU 时间。
- `fs/filesystems/procfs/src/task_nodes/root.rs` 有状态文件入口，但没有 `/proc/<pid>/statm`；`status` 目前只输出名称、PID/TGID、固定 ID 与 CPU mask 行。
- `core/ksyscall/src/task/wait.rs` 只有 `sys_waitpid`，没有 `waitid` 路由或实现。
- 当前 repo 有受证据推翻的 DRM ioctl 编号/结构体结论；以 `report/33` 的回退结论为准，不重新引入改号或错误结构体。

以上是新上游副本的事实，不能反推 T490 当前工作树也缺少同一实现：p36 build manifest 显示 T490 树包含额外的 inotify、sysfs、unix socket 等未提交修改。

## 下一步实施边界

1. 先完成 `/proc` 与 `getrusage` 内存/缺页统计的 MM 语义设计，再新增内核接口和生命周期统计；保持计数单位与 Linux v7.0 一致。
2. `waitid` 作为独立 syscall 兼容项评估；仅在支持语义及覆盖范围冻结后实现，不与内存统计混成一个补丁。
3. 多进程 renderer 继续依赖可复现轨迹定位。需要在准确记录源码/内核哈希的新证据轮中，以默认多进程命令比较 child/renderer 创建、退出状态、相关 syscall 与 DRM 访问。
4. 所有新增实现限定在内核源码。已有用户态启动脚本、测试 HTML/JS/CSS、rootfs、shim 与原证据均不修改。
