## 结论

最终候选 kernel `ac1032fe98c382cc37646a12453b7141b789c9abfe1651ff5f8f1e0263767fa2` 在正式 2 GiB、AArch64 纯 TCG、Chromium 149.0.7827.53 参数下通过初始首页 strict；首屏在 driver 启动后 371.401 秒通过。随后 nav-01 的真实 QMP `Ctrl+R` 重载通过；nav-02 在90秒重载窗口内16次 strict 采样均失败，最后保存 timeout 帧并停止发出后续重载。driver 仍完成从 `page_ready` 起的 1,805.002 秒保持，最终为1/10重载；正式 gate 返回 FAIL。

周期 QMP screendump 65/65 成功。`ppm-summary` 记录4张首个 strict 周期帧前的 warmup、65帧中59帧 strict 失败，其中55帧在第一个通过帧之后失败；首个周期 strict PASS 为 `shot-05-at0360s`。逐帧结果 [ppm-assert-shot-65-at2174s.json](../evidence/2026-11-20_t490-candidate-stability-r3/remote/ppm-assert-shot-65-at2174s.json) 显示最后帧 `strict_fail_count=6`，官方 banner 和色块均未检出；它与 nav-02 timeout PPM SHA 相同，预览均显示 Chromium “Page Unresponsive” 模态框。汇总字段 `last_pass=1` 是“本轮曾出现过 strict PASS”的旧字段（shot-05），不表示最后一帧通过。正式 gate 由 nav-02 超时及 post-pass 失败保持 FAIL。

事件归一化928/928通过。724条 guest watchdog 记录和60个 host liveness 样本中，Weston/Chrome持续存活；最后 guest uptime 2,177秒时 memfree 为530,308 KiB。没有 guest process-exit 事件或 OOM 文本。故本轮失败表现为页面/导航无响应，而不是观察到的 Browser、Weston 崩溃或 OOM。QEMU实际运行2,178秒并正常退出。

## 故障边界

首屏和第一次重载均可严格通过，第二次真实重载后出现 `Page Unresponsive`。该序列不同于两次正式候选失败中的“第八次重载卡死”及“首屏2,400秒 timeout”，说明候选存在重载次数和冷启动结果不一致的间歇性页面阻断。逐帧 JSON 已将最后周期帧的 strict 判为 FAIL；此前误读来自 `ppm-summary` 的旧 `last_pass` 字段语义，不是图像门禁漏检。R3 原始 evidence 和摘要保留原貌；后续输出已在 [report 358](358-ppm-summary-last_pass字段语义更正及round_assert摘要改进-20261120.md) 记录字段澄清。当前候选仍不稳定。

本轮只记录页面、导航和存活结果，没有启动可计入的四项性能采集；无性能收益结论。兼容性摘要仍依赖独立探针矩阵，不能由本轮重载结果替代。
