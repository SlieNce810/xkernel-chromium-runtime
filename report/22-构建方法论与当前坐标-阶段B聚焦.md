# report/22 · 在 x-kernel 上构建可稳定运行 Chromium 环境：方法论与当前坐标

- 日期：2026-09-22
- 前序：`report/20`（六阶段计划 v3）、`report/21`（阶段 A 实测 · Ozone 三元组定标）
- 定位：不是又一份阶段报告，而是回答**"怎么构建"这个总问题**的框架文档。
  后续所有阶段报告都挂在这个框架上，避免"试一个旗标写一份报告"的无结构推进。

---

## 0. 结论先行（五句话）

1. **"可稳定运行"不是一个开关，是一个必须自下而上逐层闭合的接口依赖集合。**
   六层栈（L1 平台基座 → L6 稳定长跑）中 **L1–L3 已封板、L4 半开、L5 未动、L6 未开始**。

2. **导航不提交是主问题，`rc=191` 是次问题。** 依据：阶段 A 四轮实验里 browser
   **全部存活**（`已退出 rc=` 全为"无"），但 `renderer` 计数**依然全为 0** ——
   这两件事在数据上是**互相独立**的。

3. **本轮识别出两处测量盲区，必须先补，否则后续所有实验的判读都建立在沙地上：**
   - **盲区一（日志分级）**："零表面创建日志"很可能只是 `--v=1` 级别不够，不是"真的没建表面"；
   - **盲区二（输入设备 / wl_seat）**：guest 内 `/dev/input` **只有 `event0` 一个 evdev 节点**
     （QEMU Virtio Keyboard），鼠标节点被内核丢弃（即待办 G6）；而 Chromium 每轮都报
     `No wl_seat object. The functionality may suffer.` —— 这两条此前被当作互不相关的独立缺口。

4. **方法论六条**（§3），其中 **M2 自证** 与 **M5 记账** 最反直觉、也最值钱：
   前者的代价是阶段 A 一半工时花在修测量管线（D1–D5），后者的收益是停止在
   cpuinfo / inotify 这类已被证否的方向上重复投入。

5. **战略提醒：不要把三个人都压在 L5。** 性能分（15）与文档分（10）**可以独立于渲染达成**，
   而 L5 有明确的预算上限与停止规则（`report/20 §8`）。

## 1. 问题本质

赛题要的东西可以一句话概括：**让一个 249 MB 的多进程浏览器，在一个接口集远小于 Linux 的
内核上，稳定地画出指定页面。**

它的难度不在任何单个技术点，而在三个结构性事实：

| 事实 | 后果 |
|---|---|
| **Chromium 的接口需求是一个大集合**（进程/IPC/内存/图形/沙箱/procfs…） | 缺任何一项都跑不起来 |
| **缺失的症状高度同质**：进程静默退出，不报缺什么 | 无法从症状反推缺口位置 |
| **我们拿的是预编译二进制**（248 MB，不能重编） | 只能靠运行时旗标 + 实测，不能靠改 GN 配置 |

⇒ 所以这个任务的真正难点不是"写内核代码"，而是
**在信息不足的条件下，把"静默失败"降解成一串可独立判决的小问题。**

这正是六层栈和六条方法论要解决的事。

## 2. 六层依赖栈（含判据与当前状态）

自下而上，**下层不通则上层必塌**；判定顺序不可跳步。

| 层 | 名称 | 需要什么 | 机器可判的判据 | 状态 |
|---|---|---|---|---|
| **L1** | 平台基座 | 纯 TCG QEMU ≥8.0 + `kplat-aarch64` + 组委会 `qemu_defconfig`；四类 virtio 设备 | `t490_platform_check.sh` 35 项 RC=0；`run-session.py` 15 项断言；命令行无任何 `-accel` | **已封板** |
| **L2** | 内核接口 | syscall 家族：fork/execve/wait、AF_UNIX+SCM_RIGHTS、memfd、eventfd/timerfd、epoll、signalfd、madvise、prctl、procfs、netlink | 调用点 `ENOSYS/EINVAL/EFAULT` 归零；ERROR 行归零 | **部分**（P0–P6 + G17 已修） |
| **L3** | 图形设备 | virtio-gpu → DRM `card0` → weston compositor → `wayland-0` socket | weston 存活；日志含 `Output 'Virtual-1'`；monitor `screendump` 产出非黑图 | **已达成** |
| **L4** | 窗口与 GL | Ozone Wayland 后端 + `wl_compositor`/`wl_shm`/`wl_seat` + 软件 GL（ANGLE/Vulkan/SwiftShader ICD） | `gl=none` 与 `not found in allowed implementations` 双归零；**屏幕出现 Chromium 窗口** | **部分**（GL 门禁已开；窗口创建无证据 ← 见盲区一） |
| **L5** | 导航与 renderer | 导航提交 → `RenderProcessHost` 创建 → renderer 进程 → 首帧绘制 | `type=renderer` 连续 ≥12 次快照；`ppm_assert --strict` 9/9；双帧 `--diff` 两项 PASS | **当前战场** |
| **L6** | 稳定长跑 | ≥600 s 无退出 + ≥5 次独立采样 | V1–V6 全绿；`T_*` 中位数与波动范围 | **未开始** |

**关键读数**：L4 的"部分"很特殊 —— GL 那条线是**今天刚打通的**
（`--use-gl=angle --use-angle=vulkan` 是史上第一个被接受的 GL 实现，
ANGLE 真的执行到了 `vulkan_icd.cpp:388 ChoosePhysicalDevice`），
但**窗口创建至今没有任何日志证据**。这两件事必须分开看：

- GL 通了 ≠ 窗口能建（GL 影响的是画面内容，不是窗口生命周期）；
- 而"零表面日志"这个观测本身**可信度存疑**（盲区一）。

## 3. 方法论六条（从 21 份报告的实际代价中提炼）

### M1 · 降解：把"能不能跑"降解成不可跳步的判定序列

> V1 Weston 会话 → V2 browser 存活 → V3 renderer ≥60 s → V4 页面绘制 →
> V5 JS 执行 → V6 内容正确

**为什么**：没有序列时，"跑不起来"是一个无法定位的整体；有了序列，
每次失败都能落到一个具体层，且**每一层都有对应的机器可判据**。
`report/20 §2` 给出的 V1–V6 就是这个序列的正式化。

### M2 · 自证：先让判据可信，再让程序可靠

> 一个没被验证过的门禁，比没有门禁更危险。

**代价实例**：阶段 A 一半工时花在修**测量管线本身**，而非浏览器：

| # | 缺陷 | 不修的后果 |
|---|---|---|
| D1 | `snapshot()` 每进程 fork `tr`/`awk`/`grep` → 单次迭代 13–16 s | `j=75` 需 225 s > 180 s 会话 ⇒ **观察循环被整段砍掉**，四轮没有一轮真采到数据 |
| D2 | 观察窗用计数器而非墙钟 | 隐含假设"每轮恰好 5 s"，慢快照会吃掉整轮 |
| D3 | 轮后小节在 guest 内重算、A0 还在 guest 里再起一个 chromium | C1 轮尾部小节**全部未执行** |
| D4 | `--expect-size` 用首图尺寸 | 同轮首帧 640×480、其余 1280×800 ⇒ **正确的帧被判"尺寸不符"** |
| D5 | 占位符正则 `__[A-Z_]+__` 不含数字 | 新增的 `__RUN_A0__` **漏检**，未替换的占位符被当合法参数传进 chromium |

**做法**：`ppm_assert.py` 的三重对照 —— 正向 9/9 PASS、真实历史截图负向 1/9、
差图三情形 3/3 符合预期。**判据自己没有对照实验，就不许用它下结论。**

### M3 · 隔离：一轮只改一个变量

正交短轮 180 s，单变量对照。多变量同改 ⇒ 差异不可归因。

### M4 · 差异优先：「崩的组 vs 不崩的组」比穷举调试便宜

`report/20` 原计划里的 A2（差异分析先行）就是这条。阶段 A 的实际收益也在此：
C3（`GPU_MODEL=separate`）唯一出现 `type=gpu-process`，由此把
"browser 静默退出"降解成了一个**可独立观察、有明确退出码的对象**。

### M5 · 记账：被证否的方向要立碑，禁止重复投入

**两次真实代价**：

- `Failed to initialize cpuinfo` 曾被当作唯一疑点 → 上游源码核实
  （`content_main_runner_impl.cc` 的 `PreSandboxInit()` 里**只有一条 LOG，没有 return**）
  → 推翻；两轮对照（修前 / 修后）证明 ERROR 归零但 `renderer` 依旧 0；
- `/proc/sys/fs/inotify/*` 同样：P6 补齐后 ERROR 归零，**renderer 依旧 0**。

⇒ §4 的"已证否清单"必须持续维护，否则会以"再确认一次"的名义重复烧掉整轮预算。

### M6 · 前推：症状定位点持续往前推，直到推到最小可判定动作

> "renderer 从未被 fork"（report/13）→
> "**导航卡在 `FileURLLoader::Start` 之后、提交之前**，因此根本不会去创建 renderer"（report/21 §3.2）

**为什么重要**：`renderer 未创建` 是一个**结果**，不可直接行动；
`导航不提交` 是一个**位置**，可以直接对着它做 strace。
前推一次，可行动性就上升一级。

## 5. 当前坐标：L5 展开为三个子问题

### 5.1 子问题 A（主）：导航为何不提交？

**观测事实**（`report/21 §3.2`，跨轮次可复现）：

```
04:57:49  URL to scan: file:///usr/share/html-test/index.html
04:57:52  [180:221] FileURLLoader::Start: file:///usr/share/html-test/index.html
04:57:56  AddComponentExtension Google Hangouts        ← 最后一条日志（恒定）
（此后 47 s 无任何输出）
02:32:16  rc=191 退出
```

**"最后一条日志恒定"这件事本身就是最强的线索**：四轮不同配置、跨日期、跨内核 commit，
最后一行**永远是 `AddComponentExtension Google Hangouts`**。
⇒ 卡点在一个固定的代码路径上，不是随机崩溃。

**为什么它是主问题**（本轮的判据性推理）：

> 阶段 A 四轮 browser **全部存活**（`已退出 rc=` 全为"无"），但 `renderer` 依然全为 0。
> ⇒ **导航不提交独立于 browser 死亡。** 历史上追了两周的 `rc=191` 其实是次要矛盾；
> 就算把 191 解决了，导航不提交仍然会让 renderer 不出来。

### 5.2 子问题 B：窗口/表面到底建了没有？（测量盲区一）

**观测事实**：对 `xdg_surface|shell_surface|wl_surface|wayland_window|PlatformWindow|CreateSurface|ShowWindow`
的检索在四轮 chrome 日志里 **0 命中**（`--v=1`）。

**这个观测不可直接采信，原因是日志分级**：Chromium 的 Wayland 平台层日志大量使用
`VLOG(2)` / `VLOG(3)`，`--v=1` 下**根本不会打印**。零命中可能只是"没打出来"。

**佐证**：日志里 `Binding to wl_shm version 1 but version 2 is available` 说明
**registry 枚举与绑定是通的**（能拿到 `wl_shm`），因此 `wl_compositor` 大概率也拿到了。
若 `wl_compositor` 可用，则表面创建是可行的 —— 与"零表面日志"矛盾，
矛盾只能由"分级不够"或"真的没走到那一步"之一解决。

**补盲动作（低成本，优先做）**：
```
--vmodule='*wayland*=2,*ozone*=2,*navigation*=2,*render_process*=2'
```
一轮 180 s 即可判定：是真的没建表面，还是只是没打印。

### 5.3 子问题 C：`wl_seat` 缺失是否是导航的前置阻塞？（测量盲区二）

**两条此前被认为互不相关的缺口**：

| 事实 | 来源 |
|---|---|
| Chromium 每轮都报 `No wl_seat object. The functionality may suffer.` | report/21 §3.6（当轮原样复现，非新引入） |
| guest 内 `/dev/input` **只有 `event0`（QEMU Virtio Keyboard）一个 evdev 节点**；鼠标节点被内核丢弃 | `scripts/t490/evprobe.c` 实测 + 待办 **G6** |

**G6 的机制**（已知缺陷）：`input.rs::physical_location()` 硬编码 `virtio0/input0` +
`inputdev/lib.rs` 按 id 去重 ⇒ **第二台 virtio-input（鼠标/tablet）被丢弃**。

**为什么这可能就是 L5 的钥匙**：
`--with-input` 会挂 keyboard + tablet 两台设备，而内核只注册 1 台。
如果 weston 的 libinput 后端因设备集不完整（或设备 ioctl 不完整）而未创建 `wl_seat`，
则 Chromium 的 Wayland 侧输入子系统初始化处于降级态。
**"降级"是否升级为"阻塞"，目前没有任何证据 —— 这正是要验的。**

**补盲动作**：
1. 本轮 QEMU 命令行确认含 `--with-input`（`run_session_t490.sh:51` 已带）；
2. guest 侧 `ls -l /dev/input/` + weston.log 里的 libinput 设备发现记录；
3. **修 G6**（`input.rs::physical_location()` 不再硬编码 + `inputdev` 去重改按设备而非 id）
   → 让鼠标 evdev 出现 → 观察 `wl_seat` 与 `renderer` 是否同时变化。

> ⚠️ G6 修法属于**内核行为变更**，按 `report/20 §3-C` 的分类属"新功能/行为修正类"，
> 需单独提交，不与主任务混提。

### 5.4 子问题 D（次）：`rc=191` 的归属

**已知**：C3 轮 `gpu_process_host.cc:1005 GPU process exited unexpectedly: exit_code=48896`；
`48896 = 0xBF00` ⇒ `WEXITSTATUS = 0xBF = 191`，与历史 browser 的 `rc=191` **同码**。

**关键推论**：上游 `content/public/common/result_codes.h` 里**没有 191**
（`NORMAL_EXIT=0 / KILLED=1 / HUNG=2 / KILLED_BAD_MESSAGE=3 / GPU_DEAD_ON_ARRIVAL=4`），
且 `gpu_main.cc` 在 GPU 初始化失败时返回的是 `RESULT_CODE_GPU_DEAD_ON_ARRIVAL`(=4)。
⇒ **191 不是 Chromium 定义的结果码**，browser 与 GPU 进程共用一个未定义码，
指向**共用组件**（crashpad 侧，或内核 wait 状态编码）。

**动作**：基线配置固化为
`--ozone-platform=wayland --use-gl=angle --use-angle=vulkan` + `GPU_MODEL=separate`
（去掉 `--in-process-gpu`），此时 GPU 进程是独立对象、有明确退出码，
`strace -f -p <gpu-pid>` 的临终末调用即为判决性证据。

**判读分支**：
- 末行 `exit_group(191)` ⇒ **主动退出码**，顺上游代码找触发检查点（唯一能"顺藤摸瓜"的情形）；
- 末行 `--- SIGxxx ---` ⇒ **信号致死**（191 = 128+63，对应实时信号 63），
  取 `si_addr` + `/proc/<pid>/maps` 映射到模块。

## 7. 战略：分数保护与并行

初赛 100 分构成：图形 20 / 浏览器 20 / 补丁 25 / 性能 15 / 文档 10 / 演示 10。
**达标即满分、缺证据计 0。**

| 分项 | 当前底座 | 是否被 L5 阻塞 |
|---|---|---|
| 图形 20 | Weston 稳定 + 分辨率正常 + screendump 出图 | **否**（已可取证） |
| 补丁 25 | P0–P6 + G17，多个真缺陷修复 + 幂等应用器 | **否**（继续独立积累） |
| 性能 15 | 未开始 | **否**（但需 R1 先 commit+tag、R3 补中位数聚合脚本） |
| 文档 10 | 22 份报告 + 判据工具链 | **否**（强项） |
| 浏览器 20 | browser 存活但页面不渲染 | **是**（唯一被阻塞项） |
| 演示 10 | 待定 | 部分 |

**结论**：**100 分里有 70 分不被 L5 阻塞。** 分工建议（A 内核/驱动、B 用户态/图形、C 度量/工程）：
