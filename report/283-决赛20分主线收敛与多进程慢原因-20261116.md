真正需要调整的是工作顺序。此前把 Chromium 完整源码重编译、原生 sandbox、30 分钟稳定性和性能统计放在
页面交互之前，导致诊断工作占住 T490，而评分项仍停在输入门禁。

现在采用评分优先的顺序：

1. 固定已经能出首帧的 Chromium 149 用户态、默认 Browser → Zygote → Renderer、Wayland + SwiftShader、纯 TCG。
2. 先收齐指定 HTML、双页签、JS、CSS 和真实输入的可重算 gate。
3. 只有评分链稳定后，再恢复源码诊断版和 sandbox/stability/perf 扩展。

## 为什么单进程快，多进程慢

单进程把 Browser、Blink、V8 和 compositor 放在同一地址空间。启动一次程序后，页面解析、脚本、布局和绘制
几乎没有跨进程握手。

默认多进程至少要经过 Browser → Zygote → Renderer，再建立 Mojo/ipcz endpoint、SCM_RIGHTS fd、共享内存和
DataPipe；页面响应还要从 browser/utility 送到 renderer，renderer 生成 frame，再经过 viz/Wayland 提交。
T490 是 x86_64 主机上的 aarch64 guest，正式轮禁用 KVM 使用纯 TCG。每个新进程都要重新翻译大量用户态指令，
futex/epoll 等等待也会被 TCG 放大，所以首次有效帧需要数百秒。

已观察到的关键边界：

- 静态 index 首帧在 `--ipc-connection-timeout=600` 下通过；60 秒窗口会误杀尚未完成 bootstrap 的 renderer。
- interaction 页在默认 V8 下容易卡在 renderer 冷启动；`--js-flags=--jitless` 的 A/B 已恢复页面和 JS 自检。
- swap 总量已扩到 12 GiB，解决的是编译/启动峰值的容量门槛；换入换出不能减少 TCG 指令数，过度换页还会更慢。

## 驱动修正

`interaction_score_driver.py` 的 pointer step4 路径保留真实 HMP → virtio-mouse → evdev → libinput → Weston →
Chromium 链，不注入 DOM 事件。HMP 是 QEMU 当前匿名输入设备可用的真实指针通路；`input-send-event` 在本机只返回成功、却没有到达 Chromium client 的键鼠事件，带 QEMU device id 的诊断还会使当前 QEMU SIGABRT，因此正式平台设备仍保持匿名，pointer 使用 HMP。已验证的顺序是：

- 初始页面通过真实 Tab/Enter 完成 JS 自检，再输入 `hello x-kernel`；
- 鼠标相对移动按 4 像素步进完成计数按钮点击；
- 第二次按下链接后，通过 CSS 目的页的真实 6/6 结论和输入前后 PPM 确认跳转。

为把最后一跳从 Weston 与 Chromium 之间继续分开，新增
`[wayland_input_client_gate.py](/E:/02_competition/中电杯/scripts/t490/wayland_input_client_gate.py)`。
在诊断轮打开 `WAYLAND_DEBUG=client` 后，它要求同一 Chromium client 收到
`wl_keyboard.enter/key` 和 `wl_pointer.enter/button`，避免再把 Weston eventdemo 的成功误当成页面控件已经收到事件。
