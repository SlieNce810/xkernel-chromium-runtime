# T490 `ac1032` 正式稳定性第二轮首屏超时并保持白屏（2026-11-20）

## 结论

在最终候选 kernel `ac1032fe98c382cc37646a12453b7141b789c9abfe1651ff5f8f1e0263767fa2`、2 GiB AArch64 纯 TCG、Chromium 149 和正式稳定性参数下，首屏在 2,400 秒 readiness timeout 内没有通过 strict。driver 记录 79 次 `nav-00` 轮询，没有开始 10 次重载或 1,805 秒正式保持；QEMU 在 `2,430.5` 秒后退出，正式 gate 返回 FAIL。

73 张周期 QMP 截图均为 `1280x800`，但没有一张 strict 通过。initial-timeout 和末帧 `shot-73-at2415s.ppm` 哈希均为 `197047b014d543072533cb1a4dc6d7909d288cfa358cae8ceb1f8ad3b43717aa`，与此前候选 120 秒短诊断的持续白屏帧相同。Weston 和 Chrome 的 802 条看门狗记录没有 `no`；Browser/Zygote/Renderer 进程退出事件为 0，OOM 行数为 0，末次看门狗 guest uptime 2,425 秒时仍有约 572 MiB 可用内存。

远端结果为 `STABILITY_DRIVER_RC=1`、`STABILITY_ROUND_RC=0`、事件归一化 `RC=0`、正式 gate `RC=1`；gate 原因为缺少 strict `page_ready`、hold 终点和最终结果事件。未产生可计入验收的页面稳定性或性能样本。

串口记录了 Chromium Browser argv 中的 `file:///usr/share/html-test/index.html`，并记录 `FileURLLoader::Start` 发起了该本地文件导航；因此本轮不属于“Chrome 进程完全没有启动”。这些日志不能证明 Renderer 已完成文档提交或绘制，最终 strict 门禁仍失败。首屏 timeout 截图与末帧同为纯白 SHA，也与此前候选白帧 SHA 相同。

## 与此前候选诊断的关系

相同候选在 120 秒 diagnostic-only R2 中首屏在 496.611 秒通过，8/8 导航 driver strict 通过，事件归一化也通过（[report 351](351-T490-ac1032匹配120秒诊断第二轮八次重载通过-20261120.md)）；更早的候选 120 秒诊断 R1 则从未通过首屏（[report 349](349-T490-ac1032两分钟间隔诊断未到首屏-20261119.md)）。此前正式轮在 496.759 秒通过首屏并保持 1,805 秒，但第八次重载失败（[report 345](345-T490-ac1032稳定性轮第八次重载页面无响应-20261119.md)）。

这些结果表明候选启动与页面绘制会间歇性失效；短诊断 R2 的通过不能覆盖两个正式候选稳定性失败，也不能证明故障只由长时间运行触发。每轮 `t490_round.sh` 都从固定 `BASE_IMG` 重制 `disk.img`；本轮与短诊断 R2 使用相同 `BASE_IMG` SHA `bab5c9f5…`。env 中记录的 worktree `disk.img` pre-run hash 是重制前状态，不是 QEMU 实际读入镜像的哈希。
