# 19 · 渲染闭环：阶段零–二实测与关键纠错

> 轮次：`2026-09-22_t490-fullbase`（commit `7f77919`）→ `2026-09-22_t490-inotifycpu`（commit `c2eabd5`）
> 环境：T490 `mo@10.249.63.140`，AArch64 QEMU 10.2.1，纯 TCG，4 vCPU / 4 GiB，
> 基础镜像 `images/pkg-installed.img` sha256 `56302b8f4d1c56d99f2ba6e84998448ed5caa09093ee3663fbc07c8741e091de`。

## 0. 三条结论（先说要点）

1. **`Failed to initialize cpuinfo` 完全不致命，它不是 renderer 的阻塞点。**
   上游 `content/app/content_main_runner_impl.cc` 的 `PreSandboxInit()` 里只有一条 `LOG(ERROR)`，
   没有 `return`、没有 `LOG(FATAL)`。此前把它当根因是**误判**（含 report/18）。
2. **本轮实际修实了两个接口缺口，效果可复现地验证了**（两轮同环境对照，ERROR 行归零），
   但 `type=renderer` 仍然为 0 —— 这反过来印证了结论 1。
3. **当前真实阻塞是浏览器进程本身在导航开始后硬崩（rc=191），renderer 从未被 fork 出来。**
   同时确认计划里冻结的旗标 `--use-gl=swiftshader` 在本 build 上**不存在该实现**（`gl=none`）。

## 1. 阶段零 · 现状侦察（先纠正三处流程性错误）

### 1.1 上一轮证据是被截断的，不能作为结论
`2026-09-22_t490-basic-cpuinfo` 看起来"cpuinfo 修复后 ERROR 消失"，实则**是伪证据**：
那轮 `--single-process --no-zygote` 根本不创建 zygote，而 ERROR 恰恰只由 zygote 打印。
该轮 110.8s 就被 QEMU 自行退出截断，B 路径（`--in-process-gpu`）刚开始 32s，没有任何 renderer 结论。

### 1.2 判活必须看 `/proc`，`kill -0` 会把僵尸当活
`scripts/run-session.py:704` 用 `sess.alive()`（`kill -0`）判会话存活；同理本轮自研脚本
最初也用 `kill -0 "$CPID"` 判浏览器存活 —— **僵尸进程同样返回 0**，导致"浏览器仍在运行"的假象。
本轮改为**每 5 s 全量扫描 `/proc/<pid>/cmdline` + `stat` + `task/` 线程数**，
直接以"快照里还在不在"为判据（`autorun_full.sh::snapshot()`）。

### 1.3 guest 日志不在宿主上，但 `disk.img` 在
guest 侧写的 `/root/*.log` 随 QEMU 停机而"消失"，但轮次用的 `disk.img` 留在宿主。
取回方式（后续轮次的标准动作）：

```bash
debugfs -R "dump /root/chrome-full.log /tmp/gl/x" ~/x-kernel/disk.img
```

### 1.4 轮次编排（复用现成机制，勿手写注入）

```bash
  PAGE_HTML=$HOME/xk6/scripts/testpage/local-check.html \

```
- `BASE_IMG` **必须显式指定 `pkg-installed.img`**：只有它含实体 Chromium（`249957096` 字节）；
  `t490_round.sh` 的默认值 `p0-drmversion-fixed.img` 里 chromium 是 0 字节空壳。
- 增量 `make build` 仅 **~5 s**（root.rs 改 10:10:28 → kernel.bin 10:10:59 是 31 s；本次 4.8 s），
  不要跑 `build_xk_t490.sh` 全链。

## 4. 关键纠错：cpuinfo 失败不致命

`report/18` 与阶段计划都把 `Failed to initialize cpuinfo` 当作 renderer 缺失的根因。**上游源码否证了这一点**：

```cpp
// content/app/content_main_runner_impl.cc — PreSandboxInit()
void PreSandboxInit() {
  ...
#if BUILDFLAG(BUILD_TFLITE_WITH_XNNPACK)
  // cpuinfo needs to parse /proc/cpuinfo, or its equivalent.
  if (!cpuinfo_initialize()) {
    LOG(ERROR) << "Failed to initialize cpuinfo";     // ← 只有日志，无 return / 无 FATAL
  }
#endif
  base::internal::CanUseBackgroundThreadTypeForWorkerThread();
  ...
}
```

**行为侧证据吻合**：zygote 打完这条 ERROR 之后**继续**执行到
`content/zygote/zygote_main_linux.cc:202 ZygoteMain: initializing 0 fork delegates`。
一个致命的初始化失败不可能让进程接着走到 zygote 主循环。

之所以仍值得修（两处都是真缺口）：
- `/proc/cpuinfo` 少了 ARM64 身份行 → `cpuinfo_arm_linux_parse_proc_cpuinfo()` 失败也 `return`；
- `/sys/devices/system/cpu/present` 与 `possible` **都不存在** → 首道门
  `if ((max_present | max_possible) == 0) { log_error("failed to parse both lists ..."); return; }`
  直接命中 → 全局 `cpuinfo_is_initialized` 永不置 `true`。
  该库在 ARM64 Linux 上**只有 3 条硬失败路径**（上述、calloc 失败、`/proc/cpuinfo` 解析失败），
  sysfs cache 读失败属"尽力而为"，不影响返回。

**但它们是"接口完整性修正"，不是渲染阻塞点。**

## 5. 当前真实阻塞与下一步

### 5.1 阻塞画面
```
02:30:14  browser pid=141 启动
02:31:25  FileURLLoader::Start: file:///usr/share/html-test/index.html   ← 导航已开始
02:31:29  browser 最后一条日志（AddComponentExtension Google Hangouts）
02:32:16  !! browser 已退出 rc=191   ← 无 FATAL 行、无 Goodbye、无崩溃报告
```
同一时段：zygote（179/181、221/226）在 `ZygoteMain` 后再无日志并消失；
`type=renderer` 在 30 次快照中**一次都没出现**。→ **renderer 从未被 fork 出来。**

### 5.2 下一步（按性价比排序）
1. **`strace -f` 抓 browser/zygote 临终最后一个 syscall 与信号**（镜像里 `strace` 存在，1.2 MB）。
   这是唯一能直接回答"rc=191 是怎么死的"的手段，应作为下一轮的主实验。
2. **修冻结旗标的 GL 实现选择**。`gl_factory.cc:110` 打印的 allowed 列表是
   `[(gl=egl-angle,angle=opengl),(gl=egl-angle,angle=opengles),(gl=egl-angle,angle=vulkan)]`，
   **不含 swiftshader** → `--use-gl=swiftshader` 必然落到 `gl=none`。
   而镜像里软件 GL 栈齐全：`/usr/lib/chromium/{libvk_swiftshader.so(19.7MB), vk_swiftshader_icd.json, libEGL.so, libGLESv2.so}`。
   可行组合：`--use-gl=angle --use-angle=vulkan` + `VK_ICD_FILENAMES=/usr/lib/chromium/vk_swiftshader_icd.json`
   （命中 `angle=vulkan`）。
3. `/dev/dri`（含 `renderD128`）在镜像中不存在 —— 这是 `drmGetDevices2() has not found any devices` 的来源，
   会影响 ANGLE 设备枚举；需评估是走 `--ozone-platform=wayland` 下的 shm 路径，还是补 DRM 节点。
4. 凭证：`missing credentials` 两轮稳定复现 → 属阶段三④，需在**接收侧**补 `SO_PASSCRED` 自动附带凭据。

### 5.3 对阶段计划的两点修正建议
- **阶段一冻结旗标需改**：`--use-gl=swiftshader` → `--use-gl=angle --use-angle=vulkan`（+ ICD 环境变量）。
  现旗标是"已知不生效"的，继续用它做基线会把 GL 失败一直带进每一轮。
- **阶段三①的验收判据需重写**：原判据"重建后验证 cpuinfo 初始化"在本轮已达成（ERROR 消失），
  但它**不构成 renderer 可用的证据**；阶段四的 renderer 判据应当独立于 cpuinfo 状态。
