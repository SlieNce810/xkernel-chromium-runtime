# `F_SEAL_WRITE` 写入语义修复与多进程复核（2026-11-07）

## 1. 发现

新增 memfd sealing 探针发现，x-kernel 已经能够：

- 添加并读回 `F_SEAL_WRITE | F_SEAL_GROW | F_SEAL_SHRINK | F_SEAL_SEAL`；
- 在 seal 后拒绝 grow/shrink；
- 在 seal 后拒绝可写 `mmap`；
- 未设置 `MFD_ALLOW_SEALING` 时拒绝添加 seal。

但普通 `pwrite()` 没有调用 shmem 的写入策略检查，导致：

```text
SEAL step=write_blocked FAIL rc=1 errno=0
SEAL SUMMARY pass=8 fail=1
```

## 2. 修复

`fs/filesystems/memfs/src/shmem.rs` 已有 `check_write_allowed()`，本轮把它接入：

```text
posix/fs/src/io.rs
```

覆盖普通写入、带 offset 写入和写零路径。seal 后的文件写入现在返回
`EPERM`，不再绕过 `F_SEAL_WRITE`。

新的 kernel hash：

```text
6695c68ad5d5d604f6d7f25c7fdcc45b05b552b19bfdd2114761c3e627a9e1b9
```

## 4. 默认多进程复核

证据目录：
`evidence/2026-11-07_t490-x1/`

在修复后的内核上复跑默认多进程页面，仍观察到：

```text
ChildThreadImpl::EnsureConnected()
FileURLLoader::Start: file:///usr/share/html-test/index.html
MP_RECEIPT_COUNT key=render_process count=0
MP_RECEIPT_COUNT key=navigation count=0
MP_GATE=0
MP_L3_BRANCH=stuck
```

因此 `F_SEAL_WRITE` 是真实的内核兼容性缺口，已修复并通过回归，但不是当前
多进程 HTML 白屏的充分根因。页面提交断点仍在 FileURLLoader 之后的导航回复、
renderer document commit 或 frame sink/raster 阶段。
